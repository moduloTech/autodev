# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Rails 8.1.3 application distributed as a CLI tool via Homebrew (`modulotech/tap`) that automates the implementation of GitLab issues. It polls configured projects for issues assigned to the autodev user with a `label_todo`, clones the repo, implements changes via `danger-claude`, commits, pushes, creates a Merge Request, waits for a green pipeline, then reviews the MR — with the project's own review skill when it declares a `review_skill`, else the `mr-review` binary.

`bin/autodev` is a supervisor: it boots Rails + the Solid Queue worker as child processes. `bin/rails server` serves the embedded dashboard; `bin/jobs start` runs `SolidQueue::Cli` which forks dispatcher + scheduler + worker subprocesses. The recurring `AutodevPollJob` fires every `poll_interval` seconds, discovers work via `Autodev::PollDispatcher`, and enqueues per-issue `IssueProcessJob`s that run the workflow classes (`IssueProcessor`, `MrFixer`, `PipelineMonitor`).

History: this used to be a single-file `bundler/inline` Sinatra+Sequel CLI. The migration to Rails (steps 1-8 of `docs/autospec.md` §C) wrapped 2026-06-09 with `v1.0.0-alpha.1`. See [`docs/railsification-postmortem.md`](docs/railsification-postmortem.md) for the retrospective. Phase D (AutoSpec — autospec.md §A, §E-G) is the next major feature scope; it is greenfield, not migration work.

## Running

```bash
# Production: brew install + service
brew install modulotech/tap/autodev
brew services start autodev

# Foreground from the supervisor (logs to stdout/stderr instead of ~/.autodev/log/)
autodev

# Custom config file
autodev -c path/to/config.yml

# CLI commands that read/mutate the SQLite file and exit (no supervisor):
autodev --status
autodev --errors [IID]
autodev --reset [IID]

# One-shot poll cycle (the old `--once` flag is gone — use the runner):
bin/rails runner 'AutodevPollJob.perform_now'
```

Dependencies are installed by `bundle install --deployment` at Brew install time. The wrapper at `/opt/homebrew/bin/autodev` pins Brew's Ruby on PATH (any `mise`/`rbenv`/`asdf` shim would otherwise pick a Ruby incompatible with the gems' native extensions).

Requires: Ruby ≥3.2, `danger-claude` on PATH (Brew dep), and `mr-review` (Brew dep) only for projects that declare no `review_skill` — for those, the review step is skipped when it is missing (Autodev #74). When `app.run` ports are configured, Docker Desktop is also required for Chrome MCP injection.

## Local development

The repo runs the exact same code path as production — same Devise + Entra ID SSO, same `GitlabMembershipSync` in the OAuth callback, same Solid Queue worker. There is no dev-only auth bypass: you sign in with your real Microsoft 365 account and the callback resolves your real GitLab membership. To wire that up locally:

1. **`RAILS_ENV=development`**. `config/recurring.yml`'s `development:` block is empty, so the Solid Queue scheduler boots with zero recurring tasks — a local `bin/autodev` never auto-polls production tickets. Trigger a cycle by hand: `bin/rails runner 'AutodevPollJob.perform_now'`. `bin/autodev` prints a banner at boot reminding you of this.

2. **Azure SSO credentials**. Add an `azure:` block to your local `~/.autodev/config.yml` (mirrors prod's — same client_id / client_secret / tenant_id):
   ```yaml
   azure:
     client_id: <prod-client-id>
     client_secret: <prod-secret>
     tenant_id: <prod-tenant>
   ```
   Or export `AZURE_AD_CLIENT_ID` / `AZURE_AD_CLIENT_SECRET` / `AZURE_AD_TENANT_ID` (the supervisor forwards them to the Rails + worker children). Without one of those, `config/initializers/devise.rb` falls back to `stub-client-id` and Microsoft returns AADSTS700016. `bin/autodev` warns at boot when the stub is detected; the `/sign_in` page also surfaces a banner with the setup steps.

3. **Localhost redirect URI**. Register `http://localhost:4567/users/auth/entra_id/callback` (Web platform, not SPA) on the app in the Azure portal. The Entra ID strategy does server-side OAuth, so it needs a Web redirect — and Azure allows `http://localhost` specifically as an exception to the HTTPS-only rule for public clients.

4. **GitLab token**. Set `gitlab_token` in `~/.autodev/config.yml` (or `GITLAB_API_TOKEN` env var) to a real PAT with `api` scope. `Users::OmniauthCallbacksController#entra_id` calls `Autodev::GitlabMembershipSync.for_user!` synchronously on every login — without a working token the first sign-in raises `SyncFailed` and rolls back the new User row. Same scope as prod's token.

5. **Projects table populated**. Projects live in the DB (task #9). Add them from the dashboard (**Projets → Nouveau projet**, admin-only) once you can sign in, or seed from YAML by copying the `projects:` block from your prod `~/.autodev/config.yml` and running `bin/rails autodev:migrate_projects_from_yaml`. Without at least one project row the table is empty; `GitlabMembershipSync` will then compute zero memberships for your user, mark you `disabled`, and Devise will refuse the sign-in (401) — chicken-and-egg, so for a fresh local DB seed via the rake first. The sync logs `[gitlab_sync] WARNING: projects table is empty…` when this happens — that's the symptom.

6. **Boot the dev server**. `RAILS_ENV=development bin/autodev` runs the full supervisor (Rails + Solid Queue), or `RAILS_ENV=development bin/rails server -p 4567` if you only need the web UI and will trigger jobs by hand.

The first dev sign-in inserts your `users` row, runs the GitLab sync, and lands you on the dashboard with your prod memberships visible — exactly the prod flow. Re-running the sync after manual edits to `project_memberships` in dev: `bin/rails runner 'SyncGitlabMembershipsJob.perform_now'`.

## Configuration

Settings are resolved in 4 layers (highest priority wins):

1. **Defaults** — `poll_interval: 300`, `max_workers: 3`, `pickup_delay: 600`, `stagnation_threshold: 5`, `pipeline_watch_max_days: 14`, `fix_verification_max: 10`
2. **Config file** — `~/.autodev/config.yml`
3. **Environment variables** — `GITLAB_API_TOKEN`, `GITLAB_URL`, plus `AUTODEV_HOME` (default `~/.autodev`), `AUTODEV_DB`, `AUTODEV_QUEUE_DB`, `AUTODEV_MAX_WORKERS`, `AUTODEV_POLL_INTERVAL`
4. **CLI flags** — `-c`, `-d`, `-t`, `-n`, `-i`

### Numeric settings: type and range (`NumericSettings`)

Every numeric setting — global or per-project — declares its **type** and its **acceptable range** in one line of `NumericSettings::SPECS` (`lib/autodev/numeric_settings.rb`). Adding a numeric setting means adding that line; there is no second place to update.

The two are deliberately separate (Autodev #58). `Config::INTEGER_FIELDS` used to answer both with one list, and every setting that needed something other than "> 0" became a special case or an omission — which is how the only two settings that drive a *safety net* ended up unguarded. `mr_review_timeout` had no ceiling, and it is a term of `HealthReport#longest_worker_timeout`, so a dropped digit (`86400000` for `86400`) widened `stuck_active_after` to years and silently switched off both the dormant audit and the "Issues bloquées" card. `pipeline_watch_max_days` was kept *out* of the list because `0` is meaningful there (it disables the age bound), which left it with no coercion at all, so a non-numeric value read as `.to_i` → `0` → bound disabled, in silence.

- **Type**: `NumericSettings.integer(raw)` returns an Integer or `nil`. It never turns a non-numeric value into `0` (and reads strings in base 10, so `'010'` is 10, not 8). `Config.load` coerces a numeric string and **leaves a non-numeric value exactly as written**, so the validator can name it.
- **Range**: a closed `[min, max]`. `min: 0` is how a field says "0 is a sentinel" (`pipeline_watch_max_days` = bound disabled, `clone_depth` = full clone) — a statement about the range, not permission for anything that coerces to 0.
The one number that is not a config key still declares both: `Autodev::ReviewArrearsSweep::LIMIT_SPEC` (`1`…`10`) is the range of the `LIMIT` env var the #88 rake reads, built from `NumericSettings::Spec` and enforced by `ReviewArrearsSweep.limit_from`, which raises `ConfigError` before a row is examined. It lives on the class rather than in `SPECS` because `SPECS` is the registry of settings read from `config.yml` and the DB, and `LIMIT` is neither.

- **Bounds in force**: the three worker timeouts (`dc_timeout`, `post_completion_timeout`, `mr_review_timeout`) are `60`…`21_600` s (6 h — 6× the largest baked default, 8× the longest successful mr-review on record, and what caps the dormant-detection window at 12 h); `pipeline_watch_max_days` is `0`…`365`; `fix_verification_max` is `0`…`100` (`0` = the MR-fix verification off, Autodev #79); the counters (`max_retries`, `stagnation_threshold`, `infra_recheck_max`, `dormant_audit_max`) are `1`…`100`; the spacings (`retry_backoff`, `pickup_delay`, `infra_recheck_backoff`, `dormant_audit_backoff`) are `1`…`86_400` s.

Where a rejection surfaces:

| Source | Layer | Behaviour |
|---|---|---|
| Global key in `config.yml` | `ConfigValidator.validate_numeric_settings!` | `ConfigError` → `bin/autodev` exits 1 |
| Per-project key under `projects:` | `ProjectValidator.validate_numerics!` | `ConfigError` → `bin/autodev` exits 1 |
| `projects` table column | `Project`'s `numericality` (type) + `#validate_numeric_ranges` (range) | invalid record; the dashboard form re-renders 422 with a localized message and the accepted range |
| A row already in `projects` | `bin/autodev`'s `warn_rejected_numeric_settings` | boot **warning** naming project, field, value and range — never a refusal, or there would be no dashboard left to fix it from |

Implementation:
- Controllers live under `app/controllers/`. Each one `include ::Web::Helpers` to gain access to `app_config`, `dashboard_kpis`, `project_overview_stats`, etc.
- Phlex views live under `app/components/web/views/**/*.rb` (autoloaded via `config.autoload_paths << app/components`). Constant names are `Web::Views::Dashboard`, `Web::Views::Components::StatusPill`, etc.
- The `errors` tab's watch cards (`Web::Views::Concerns::WatchCards`) distinguish, per row, a `error` request a pass will pick up on its own from one no pass ever will (Autodev #103) — reading the same rule `DormantAudit#error_arm` audits by: `stranded_error?` is true when `next_retry_at` is NULL or `retry_count` exceeds the project's `max_retries`. Before this every `error` card rendered identically whether the row retried itself in four minutes or was permanently stuck, and the dashboard's 401 card said credentials were dead without saying which requests that had stranded.
- Helpers live under `app/helpers/web/{helpers,i18n_helpers,issues_filter,turbo_stream_helpers}.rb`.
- `Web::EventBus` (`app/services/web/event_bus.rb`) is an in-process pub/sub (Mutex around `Array<Queue>`). `ActivityEvent.after_create_commit` publishes; `/stream` subscribes. Backpressure drops events past 100.
- `Web::config` accessor (`app/services/web.rb`) holds the loaded `~/.autodev/config.yml` hash; populated by `config/initializers/load_autodev_config.rb` on Rails boot.
- Persistence: every AASM transition + every `ActivityLogger.post` writes an `activity_events` row (`kind: 'transition'` or `'danger_claude'`; `ActivityLogger.heartbeat!` is a third writer, `kind: 'heartbeat'` — Autodev #50). A `post` carrying `replace_pattern:` **supersedes** its previous occurrence instead of appending — one rule for the GitLab note line and the DB row (Autodev #53); `created_at` moves forward, so `Issue.without_activity_since` keeps reading the freshness Autodev #50's invariant depends on. Hooks live in `Issue#emit_activity_event!` (AR) and `ActivityLogger.persist_event!`, both wrapped in `rescue StandardError`.
- Retention on `activity_events` is a **sliding window over the machinery kinds only** (`ActivityEvent::MACHINERY_KINDS` = `poller`, `error`, `usage`, `heartbeat` — Autodev #57 — plus `review_skill` since Autodev #81). `Autodev::ActivityEventJanitor`, run daily by `PruneActivityEventsJob` (`config/recurring.yml`, production only), deletes those rows past `12 × HealthReport#stuck_active_after` — 24 h at default settings. The window is **derived** from that one, and `monitoring.activity_event_retention_seconds` is a floor rather than a ceiling, because `Issue.without_activity_since` counts heartbeats: purging one inside the stuck window would make a live worker look dormant and let `dispatch_dormant_audit` reposition its row. The business kinds (`transition`, `danger_claude`, `discussions_snapshot`) are never deleted — they are the audit trail the issue timeline renders, and #53's collapse already bounds them per issue. The one-shot `bin/rails autodev:compact_activity_events` (Autodev #53) is for the pre-#53 arrears, not for growth.
- `ActivityEvent.user_visible` is the single definition of "a row somebody asked to see" (= not a machinery kind). The issue timeline, the dashboard sparkline (`Web::Helpers#weekly_activity_counts`) and the `/stream` guard all go through it; the same set is what the janitor is allowed to delete. `Issue.without_activity_since` deliberately does **not** use it (Autodev #50).
- Localhost only by default (`web.bind: 127.0.0.1`). Expose via reverse proxy / NetBird if needed; autodev itself stays plain HTTP, no built-in auth gate on the dashboard (Devise is wired for AutoSpec — phase D — but no `before_action :authenticate_user!` is applied to the existing routes).
- Localized: views use `t_web(key, **vars)` → `Locales.t(key, locale: ...)`. Strings live in `config/locales/{notifications,activity,web}.{fr,en}.yml`. Locale comes from `web.locale` (default `fr`).

## Architecture

### Process topology

```
bin/autodev (supervisor parent)
├── bin/rails server   → Puma → Rails dashboard
└── bin/jobs start     → SolidQueue::Cli → forks:
    ├── solid-queue-dispatcher  (claims scheduled jobs)
    ├── solid-queue-worker × N  (perform AutodevPollJob, IssueProcessJob)
    └── solid-queue-scheduler   (fires config/recurring.yml entries)
```

`lib/autodev/supervisor.rb` owns the parent. All children run in the supervisor's own process group (no `pgroup:` on `Process.spawn` — that option is `ProcessRunner`'s, for the danger-claude/mr-review subprocess trees, a different concern). SIGINT/SIGTERM trap → flag → `wait_loop` exits → TERM all children, 10s graceful grace, KILL stragglers. If any child crashes the supervisor tears the rest down. `run` wraps `spawn_all` + `wait_loop` in an `ensure` around `shutdown_children` (Autodev #92): any abrupt end — an exception mid-`spawn_all`, an exception out of `wait_loop`, a signal the trap does not cover — still tears down every already-spawned child, which `KeepAlive: Crashed` in the LaunchAgent plist makes essential — launchd restarts a crashed supervisor, and a child it did not reap survives it and keeps the SQLite file + WAL + SHM open. **Measured, and no more than that**: the plist carries `KeepAlive/Crashed` and no `AbandonProcessGroup` key, the whole live tree shares one pgid, and 39 of the last 63 boots ended with a `rails-server` spawn and no further supervisor line. Whether launchd distinguishes a deliberate stop from a crash-restart when it signals the group is **not** established — Apple documents the key as acting "when a job dies", without that distinction — so nothing here depends on it (the alpha-53 neutral review found the earlier claim load-bearing for a `ppid == 1` filter that was itself wrong). A `SIGKILL` leaves nothing to run, so `Autodev::BootGuard` (`lib/autodev/boot_guard.rb`) runs once before `bin/autodev` spawns anything. It reaps a holder of the database file it can positively identify as an abandoned child of a **previous** supervisor, and the discriminator is the **process group**, not `ppid == 1`: the holder on the queue side is `solid-queue-worker`, a grandchild whose parent is the fork supervisor, so after a SIGKILL it keeps that parent and `ppid == 1` never matched the very case the guard exists for. The whole tree shares one pgid, an orphaned tree keeps the dead supervisor's, so the test is "this pgid is not mine **and** its leader is gone" — which also leaves a still-running sibling supervisor's tree alone. Anything else holding the file is **named in a warning and the boot proceeds**: this runs after `bootstrap` → `setup_database`, so the booting process holds the database itself, and a third-party process can hold them too — the container VM danger-claude runs in was measured holding all three at one point and none of them a day later, so it is transient rather than permanent, though the booting process alone is already enough — refusing there made autodev unbootable in a loop under `KeepAlive: Crashed`. A false refusal is a total outage; a false pass is one ghost process the `ensure` above now prevents from recurring. `AUTODEV_BOOT_GUARD_STRICT=1` restores the refusal for an operator investigating by hand. Nothing holding the file is a silent pass.

### State Machine (AASM)

The `Issue` model (`app/models/issue.rb`) mounts AASM via `include AASM`. State machine logic lives directly in the AR model — the legacy `IssueBehavior` module was inlined during step 2 second half.

**States (16):** `pending`, `cloning`, `checking_spec`, `implementing`, `committing`, `pushing`, `creating_mr`, `reviewing`, `checking_pipeline`, `fixing_discussions`, `fixing_pipeline`, `running_post_completion`, `answering_question`, `needs_clarification`, `done`, `error`

`after_all_transitions :persist_status_change!, :emit_activity_event!` writes the row + emits an `activity_events` row on every transition. **`persist_status_change!` refuses a transition decided on a state the database no longer holds** (Autodev #97): it compares the row's `status` against `aasm.from_state` and raises `StaleTransitionError` rather than saving. That is the one place the rule can be written for every transition, and it is what makes a human's gesture hold against work already in flight — a danger-claude call runs ten to sixty minutes, and `save!` writes every dirty attribute over the top of whatever happened meanwhile. It is not atomic (read and save are two statements) and does not claim to be: the window it closes is the one that existed.

### IssueProcessor

Handles the sequential flow from `pending` through `checking_pipeline`:
`start_processing!` → clone → `clone_complete!` → check spec → `spec_clear!` → implement → `impl_complete!` → commit → `commit_complete!` → push → `push_complete!` → create MR → `mr_created!` → `checking_pipeline`

For question/investigation tickets (no code changes needed): `question_detected!` → investigate codebase → post answer → `question_answered!` → `done`.

### MrFixer

Handles `fixing_discussions`: clones the MR branch, fetches unresolved discussions, fixes each one via `danger-claude -p` + `-c`, **verifies the correction**, resolves the threads that passed, pushes. Includes discussion stagnation detection. Fires `discussions_fixed!` → `checking_pipeline`.

The fetch itself lives in `MrDiscussions` (`lib/autodev/mr_discussions.rb`), shared with `PipelineMonitor` — one definition of "the unresolved threads of an MR" since Autodev #62, because the two copies were free to diverge and one of them was the delivery verdict. `MrFixer` maps its own `build_discussion` shape (title + notes, for the prompt) over the shared list.

**Autodev never resolves a discussion it has not verified** (Autodev #79). Between the `-c` commit and the resolution sits `FixVerifier#verify_fix`: `git diff <the sha the thread started on>..HEAD` — this thread's correction, not the round's — plus the original finding, handed to one **fresh** `danger-claude -p` that answers `{"verdict":"addressed|not_addressed","reason":"…"}` in a `/tmp` contract file (`VerificationContract`, the `ReviewContract` idiom of Autodev #74). Only `addressed` resolves. Three things follow from the invariant, and each is load-bearing:

- **The verifier is not the fixer.** No `resume:` (the fix loop resumes one session across a round's threads; reusing it here would be the same defect one layer down) and no `-a mr-fixer` (an agent whose whole instruction is how to correct).
- **The verifier is not a reviewer.** The prompt confines it to "does this diff address this finding" and forbids hunting for other defects. That asymmetry is PowerPanne's own review skill's: it prescribes verifying each fix after triage and forbids re-running the adversarial pass on the corrected commit, because an adversarial pass produces findings on any code and the loop never converges.
- **Every non-yes leaves the thread open** — the #62 direction applied to a danger-claude call, since the neutral value here (`addressed`) is the one that closes a review thread for good. Three causes, three activity entries, one consequence: `discussion_unverified` (the verdict), `discussion_unchanged` (no diff at all — answered without spending a call), `discussion_unverifiable` (the check could not be performed at all — `git` declined to answer, the pass crashed, or the contract is absent/off-schema). `correction_diff` has no `nil` in its vocabulary for exactly that reason: an empty String is the fact "this changed nothing", and both ways of not getting an answer raise `GitError`, so a failing `git` — which reports a non-zero status and an empty stdout, byte-for-byte what "nothing changed" looks like — cannot be read as the fact. `RateLimitError` / `AuthenticationError` travel to `execute_fix_cycle` untouched, like at every other `danger_claude_prompt` call site. An open thread is re-read next round and, if nothing moves, `stagnation_threshold` rounds later the existing `stagnation_discussions` give-up hands the ticket to a human; a wrongly resolved thread has no such recovery.

The cost is bounded by `fix_verification_max` (per-project → global → baked **10**; `NumericSettings` range `0`…`100`, `0` = check off, i.e. the pre-#79 behaviour). It caps how many corrections **one round** verifies and therefore how many threads it attempts at all — the overflow is deferred to the next round with an activity entry, never fixed-but-unchecked, so the bound and the invariant do not compete. 10 comes from production: over the 94 fix rounds on record the unresolved-thread count runs 1…18 (mean 7.6) and 81% of rounds carry ten or fewer. The stagnation signature is still taken over the threads the round *found*, not the ones it resolved — "the same discussions are still open" is the question it answers, and a round that resolved none of them is exactly the case it exists to end. The success line counts what was **resolved**, and a round that resolved nothing says so under its own key, `discussions_none_resolved`. That decision lives in one method (`report_round`) because it has two sinks and they are both GitLab: `notify_localized` posts a comment, and `log_activity` writes into the activity note on the same issue — guarding only the first left the other posting "0 discussion(s) corrigee(s)" anyway.

### PipelineMonitor

Handles `checking_pipeline`: fetches MR head pipeline via GitLab API.

- **MR no longer `opened`** → the pipeline is not checked at all, and what happens next depends first on whether the state carries a verdict at all (Autodev #69), then on whether anything was delivered (Autodev #66). `merged` → `mr_closed!` → `done` + `label_done`: a real delivery. Every other state — `closed`, anything GitLab adds later — → the shared abandon point (`abandon` event, `needs_attention: mr_closed_unmerged`, `label_attention`, ticket handed back to its author, comment). The split is on "was this delivered", not on GitLab's state vocabulary: posing `label_done` on a rejected MR announced it as `Development::Awaiting Feature Review`, and leaving the row unflagged put it in `dispatch_done_unassigned`'s population, so #60's `post_completion` guard did not apply to it. An unknown state keeps taking that route on purpose — erring towards "a human should look" is recoverable, erring towards "ready for feature review" is not
- **MR `locked`** → nothing is concluded (Autodev #69). GitLab's MR state machine declares exactly four states (`opened`, `closed`, `merged`, `locked`) and `locked` is the only one carrying no verdict: `MergeRequests::MergeService` wraps the whole merge in `merge_request.in_locked_state`, and the REST reference calls it "short-lived and transitional". So it is read like a `running` pipeline — the poll leaves the row in `checking_pipeline` and the next cycle decides. Read as a verdict it abandoned an MR *in the middle of being delivered*: a public comment saying it had been closed without being merged (false), the ticket handed back, `needs_attention`, no end label. The list is an allow-list, `MrState::TRANSIENT_STATES` — one definition for all five readers of `mr.state` since Autodev #72 — so a state GitLab adds tomorrow stays in the abandon category. The wait is **not** unbounded: the transient branch falls through to `abandon_expired_watch` rather than returning early from `poll_open_mr`, so an MR wedged in `locked` is given up at `pipeline_watch_max_days` like any other frozen watch — and it deliberately does not raise `poll_inconclusive!`, which would stand that bound down
- **Running** → skip
- **Green + review_count == 0** → `reviewing`, then `review_done!` → `checking_pipeline`. `launch_review` forks here on `@project_config['review_skill']` (Autodev #74): unset → the `mr-review` binary, as before — **which clones too**: it `git clone --branch <source_branch>`s the MR into `/tmp/mr-review_<mr_iid>_<pid>`, runs every command it delegates with `chdir:` into that clone, and the `CLAUDE.md` its review prompt asks for is that clone's, never autodev's (Autodev #77 was opened on the opposite reading of it; a `grep` for `Dir.chdir` misses the `chdir:` keyword `system`/`Process.spawn` take, and a `grep` for `git clone` misses a `git!` helper that prefixes the word itself). Consequently the working directory autodev starts it in is indifferent, and is a declared neutral one (`Dir.tmpdir`) rather than the worker's inherited cwd; declared → `SkillReviewer#review_with_skill` clones the MR branch into a scratch work dir, **overlays the declared skill read off the branch that decides** (Autodev #89 — see the key design decisions), injects the project's skills, and runs the declared one via `danger-claude -p`, which writes its findings to a contract file instead of GitLab (see Key Design Decisions) — `ReviewPublisher` then posts them. Either path answers with a named outcome, dispatched by `dispatch_review_outcome` (Autodev #107 replaced the old true/false/`:inconclusive` axis: `false` was never a verdict on the merge request, it was three unrelated causes wearing one boolean). `true` → `finalize_review_success` (review count incremented only on success). `:unusable_output` (skill path only — the contract file is absent or off-schema) → `finalize_review_failure`, unchanged: the one cause that is about *this* request meeting *this* skill, so a per-request budget (`review_failure_count`, capped at `REVIEW_FAILURE_THRESHOLD`) is the right instrument. `:inconclusive` (skill path only — GitLab had not computed the MR's `diff_refs` yet, so nothing could be published), `:tool_unavailable` (`danger_claude_prompt` raised; `mr-review` timed out, crashed, or exited non-zero — its exit status carries no verdict autodev can read, so the binary path spends this budget on nothing but success any more) and `:clone_failed` (the skill review's own clone did not complete — reversing the Autodev #74 fix-round-1 choice to count it, since Autodev #96 measured this as routine GitLab flakiness) all → `resume_watch` straight back to `checking_pipeline` with **neither** counter touched and the watch clock preserved, so the next poll runs the whole review again without the age bound having been quietly reset. The bound on all three is that age bound and nothing else: **no activity row is written per poll** (the alpha-53 neutral review measured that one takes the row out of `Issue.without_activity_since` and therefore out of all three of `DormantAudit`'s arms for the whole outage, which is what `launch_review`'s own comment gives as its reason for not rescuing and resuming), and **no per-cause counter** either — one was tried and removed, being inert on a message that carries git's connect timing and a hair trigger on one that does not. The two causes are told apart in the log. `mr-review` being *absent* is not in this family at all: it is `:tool_missing`, a configuration fact, and gives up at once — see the error catalogue. Nothing is allowed to *escape* `launch_review` either: `pipeline_green!` fires before it, so the row is in `reviewing`, and `dispatch_pipelines` selects `checking_pipeline` only — an escaping exception parks the row where no pass re-reads it. Three arms cover the three classes the skill path can raise that the binary path could not (`ApiUnavailableError` → back to the watch then re-raise, `RateLimitError` → `handle_rate_limit`, `AuthenticationError` → `handle_auth_failure`), and a fourth since Autodev #81 gives the request up under a reason that names the cause (`MissingReviewSkillError` → `abandon_issue(:review_skill_missing)`) rather than letting it park in `reviewing`; a bare `ConfigError` keeps escaping on purpose, see the error catalogue
- **Green + review_count > 0 + no discussions** → `done`. The unresolved-thread list is *read* before any side effect of the green branch, and a GitLab error on that read aborts the poll instead of answering `[]` (Autodev #62): "no unresolved thread" is the delivery verdict, so it may only ever come from GitLab having said so
- **Green + review_count > 0 + discussions** → `fixing_discussions`
- **Green + review_count >= MAX_REVIEW_ROUNDS (3)** → `done` with alert, via the shared abandon point (`abandon` event, `needs_attention: review_limit_reached`, ticket handed back to its author). Not via `pipeline_green` — that event no longer has a `done` transition of its own for this case (Autodev #60)
- **Red (code)** → `pipeline_failed_code!` → `fixing_pipeline` → `pipeline_fix_done!` (with stagnation detection)
- **Red (infra/uncertain, first time)** → retrigger once, recheck next poll
- **Red (infra, after retrigger)** → stay in `checking_pipeline`, but track the failure signature; once the same infra job set recurs `stagnation_threshold` times, bail via `handle_stagnation` → `abandon_issue` → `done` + `needs_attention` (`stagnation_pipeline`) + reassignment to the author, so a never-recovering infra/deploy job can't poll forever
- **Manual/skipped** → verdict taken on the **blocking jobs** instead of the roll-up status (`allow_failure: true` jobs and unplayed `manual` gates excluded): no blocking job `failed` → `handle_green`, one or more failed → `handle_red`. `manual` is the normal end state of a green MR on any project whose pipeline ends with a manual `deploy_review`, so treating it as "wait" waited forever (Autodev #51). A GitLab error fetching the jobs leaves the row untouched for the next cycle — never read as green
- **Canceled** → stay in `checking_pipeline` (manual intervention needed)
- **Any poll that ends without a transition *and did read a pipeline status*, on a watch older than `pipeline_watch_max_days` (default 14)** → `abandon` → `done` + `needs_attention` (`pipeline_watch_expired`) + `label_attention` (Autodev #63 — never `label_done`, which reads "ready for feature review") + reassignment to the author + GitLab comment. The absolute age bound (Autodev #53): stagnation detection is fed only from `handle_red`, so a pipeline that is never `failed` — `manual`, `canceled`, `skipped`, or stuck at `created` — accumulated no signature and was polled forever. Checked *after* `dispatch_pipeline` and only while the row is still `checking_pipeline`, so a green pipeline on day 15 still completes. Clock: `issues.checking_pipeline_since`, written by an AASM callback on every transition and seeded by `PollTracker` for the rows that arrive through `update_all`. `0` disables the bound. A poll that could not conclude never expires a watch (Autodev #56), by **two** mechanisms for two shapes of "concluded nothing": a GitLab read that failed **aborts the poll** with `ApiUnavailableError`, and since the bound is the last statement of `poll_open_mr` control never reaches it (Autodev #62 — before that the job fetches swallowed the error into `nil` / `[]` and had to raise the flag by hand); a poll that read GitLab fine but could not *act* returns normally and raises the per-poll flag `poll_inconclusive!` (cleared at the top of every `check`) — both Claude-quota deferrals and a danger-claude evaluation that could not be performed. An infrastructure failure or a quota outage must never be the reason a 14-day-old ticket is given up — abandoning is terminal and `pipeline_watch_expired` is excluded from `dispatch_infra_recheck`, so nothing re-arms the row.

Pipeline fix strategy: full job logs are written to `tmp/ci_logs/<job_name>.log` files in the work directory (no truncation). Prompts reference these files by path so danger-claude reads the complete log. Each failed job is fixed in a separate danger-claude call + commit (same pattern as MrFixer's per-discussion approach).

### PollDispatcher + IssueProcessJob

`app/services/autodev/poll_dispatcher.rb` runs one polling cycle per call: discovers issues from GitLab + DB, enqueues an `IssueProcessJob(project_path, issue_iid, action)` per work item. Eight dispatch passes per project:

- `dispatch_new_issues` — new `label_todo` issues → `:process`. Also the pass that re-reads a request parked in `needs_clarification`: `process_issue` → `skip_existing?` → `clarification_received?` is the only place that asks whether the human answered. It gets there because `PollRouter#route_by_state` tests `Issue::PROCESSABLE_STATES` (`pending` + `needs_clarification`) rather than `== 'pending'` — one declaration, also read by `IssueProcessJob::DISPATCHED_FROM[:process]`, which had accepted `needs_clarification` all along while the router did not (Autodev #75). The request stays in this pass's population while it waits, because `SpecChecker#post_clarification` reposes the entry label (`apply_label_todo`) instead of leaving the ticket on `label_doing` — one poll cycle, one `client.issue` read, no write while nothing changes. `bin/rails autodev:recheck_clarifications` (`Autodev::ClarificationSweep`) is the arrears only: nothing reposes a label on a request that was already parked when the fix shipped. The sibling arrears of Autodev #88 is `bin/rails autodev:recheck_review_arrears` (`Autodev::ReviewArrearsSweep`): the requests given up on `review_failures_exhausted` with `review_count` still at 0 go back to `checking_pipeline` through `PollRouter#resume_never_reviewed`, at most `LIMIT` (default 3, ceiling 10 — `ReviewArrearsSweep::LIMIT_SPEC`) per run, behind `APPLY=1`, with a strict ownership filter that two flags widen in order — `INCLUDE_AUTHOR_HANDBACK=1` for the rows autodev's own `abandon_issue` handed back to their author, `INCLUDE_HUMAN_HELD=1` for a ticket held by any one person (Autodev #98: 4 of the 20 rows are held by somebody who is not the author). Both keep the protection that matters, which is that nobody has touched the row since the give-up — no human comment on the ticket, no human note on the **merge request**, no workflow label moved by somebody else — so a person actively working the ticket is declined whatever the tier. The merge request is the third of those and was missing until Autodev #98: the other two ask the ticket, while reviewing the merge request is the gesture a reviewer actually makes, and `HumanActivity` now owns both halves of the question. A re-arm writes the working label first and reads the ticket back before transitioning anything (`manage_labels` answers a GitLab error with `[]`, so the write is silent when it fails), **takes** the ticket rather than joining it — GitLab Community holds one assignee, so the union it used to write was accepted and ignored — and does that out loud: a GitLab comment names the person it was taken from and promises the handback, `issues.displaced_assignee_id` records who, and `IssueNotifier#handback_target` reads it so the ticket goes back to them and not to the author. The assignment write is **read back** for the same reason the label write is: it is the one GitLab Community can accept and ignore. It also records its own origin on the `transition` row — the marker `swept_before?` reads, because `reenter_to_check_pipeline` has three writers and its bare presence is not this sweep's signature. Neither is a pass, and neither may become one — see the class headers
- `dispatch_pipelines` — `checking_pipeline` rows → `:check_pipeline`
- `dispatch_discussions` — `fixing_discussions` rows → `:fix_discussions`
- `dispatch_unassignment` — active rows closed on GitLab, no longer assigned, or handed over via the labels → `closed` inline (no job). One `@client.issue` read answers all three questions
- `dispatch_done_unassigned` — `done` rows **not flagged `needs_attention`** with `post_completion` configured → `:post_completion`. The flag excludes every give-up path: the hook is for delivered work (Autodev #60)
- `dispatch_dormant_audit` — rows that stopped moving (orphaned `pending`, spent-budget `error`, worker-pruned active states) → closed / re-armed inline, at most `dormant_audit_max` times per row
- `dispatch_retries` — `error` + `pending` with backoff elapsed → `:retry_errored` / `:retry_stuck`
- `dispatch_infra_recheck` — `done` + `stagnation_pipeline` rows → `:recheck_infra`, which **asks whether anybody has touched the row since the give-up** and only then reclaims the assignment before re-entering `checking_pipeline` (Autodev #93/#106, gated by the alpha-53 neutral review). That question is `Autodev::UntouchedSinceGiveup`, extracted from `ReviewArrearsSweep` so both passes ask the same one: no human comment on the ticket, no human note on the merge request, no workflow label moved by somebody else. This pass's own query selects on status, flag, reason, MR and clocks and on nothing a person did, so without the gate a human who took an abandoned ticket back and fixed the CI lost the assignment (GitLab Community: one assignee) to a comment telling them their infrastructure had recovered. A read GitLab could not answer declines the re-arm for the cycle rather than proceeding — an unreadable ticket is never permission to take it

`app/jobs/issue_process_job.rb` is a single ActiveJob class that dispatches on the action symbol to the right worker class. `limits_concurrency to: 1, key: "issue-#{project}-#{iid}"` serializes work per ticket; the queue.yml `threads` setting (`AUTODEV_MAX_WORKERS`, default 3) caps global concurrency.

Before dispatching, `perform` checks the row against `DISPATCHED_FROM` — the status the pass that enqueued the action selects on — and logs a skip if it no longer matches (Autodev #61). Every pass enqueues its whole population each cycle, so a job that outlives the poll interval leaves duplicates behind it, and `whiny_transitions: false` means the state machine answers those duplicates with a silent no-op instead of a stop: the side effects that follow the event (GitLab comment, end label, reassignment) run anyway. This is the *staleness* guard and is orthogonal to `limits_concurrency`, which is the *concurrency* guard.

`app/jobs/autodev_poll_job.rb` is the recurring entry (`config/recurring.yml`, default `*/5 * * * *`). Probes `danger-claude` once per cycle via `Autodev::UsageGate.probe!`, backed by `UsageChecker#verdict` — one of `available`, `quota_exhausted`, `auth_refused`, `binary_missing`, `broken`, `unknown` (Autodev #108, replacing the boolean `#available?`). Since Autodev #46 this gates only the passes that reach danger-claude, not "the polling" itself; since Autodev #108 a tool fault (`auth_refused`, `binary_missing`, `broken`) closes the gate exactly like an exhausted quota, because implementation, review and discussion fixing all depend on the same call.

Both jobs wrap the ActiveJob `logger` in `Autodev::JobLogger` (`app/services/autodev/job_logger.rb`) before handing it to workflow classes — the legacy `AppLogger` accepted `info/warn/error(msg, project: path)` kwargs that Rails' `Logger` rejects.

## SQLite Schema

Two SQLite files:
- `~/.autodev/autodev.db` (primary): `issues`, `activity_events`, `users`, `projects`, `project_app_commands`, `project_memberships`, `sessions`, `schema_migrations`, `ar_internal_metadata`.
- `~/.autodev/autodev_queue.db` (queue): 10 Solid Queue tables.

AR migrations live under `db/migrate/` (primary) and `db/queue_migrate/` (queue). `config/initializers/auto_migrate.rb` runs both on Rails boot — idempotent, every `create_table` is `if_not_exists: true`. The same migration handles fresh installs and upgrades from the pre-rails Sequel-created prod DB.

**Who migrates, and what happens when it fails (Autodev #55).** `bin/autodev` requires `config/environment` before it reaches `run_supervisor`, so the **parent plays the pass first and alone**; the two children then boot their own Rails apps and play it again, which is a no-op in the normal case and the safety net for a child restarted on its own. SQLite reports `supports_advisory_locks? == false`, so Rails does not serialise two migrators: the loser of a boot race fails on `duplicate column name` or on the UNIQUE insert into `schema_migrations`, harmlessly, because the winner created the column. `Autodev::MigrationStatus` (`lib/autodev/migration_status.rb`) separates that case from a real failure:

- **the initializer never raises** — it logs a `warn` for a recognised race and an `error` otherwise, naming what is unapplied. It sits on the boot path of `bin/rails runner`, of `autodev --status` / `--errors` / `--reset`, of a standalone `bin/rails server` and of the test suite, all of which must keep booting;
- **`bin/autodev` refuses to start** when the pass left anything unapplied (`ConfigError` → exit 1, before any child is spawned). The predicate is a set difference between the migration files and `schema_migrations`, not an interpretation of the exception, so a benign race cannot trip it. The supervisor is the only entry point that refuses, because it is the one that starts the workers — a worker on an incomplete schema raises `NoMethodError` in `Project#to_project_config` on every job;
- **`/admin/health` carries a `migrations` card** (`down`, so `/healthz` answers 503) for the entry points that do boot. Only the `schema_migrations` half of the difference is re-read per call; the migration *file* list is memoised for the life of the process (Autodev #60), because it cannot change while autodev runs and `/healthz` is polled by external probes.

## Error Handling

| Case | Behaviour |
|------|-----------|
| `danger-claude` not installed | Abort at startup |
| `mr-review` not installed | Warning at startup **only if at least one project declares no `review_skill`** (Autodev #74, spec §7). A request that reaches the review step on such a project answers `:tool_missing` and is **given up at once** under `review_tool_missing` — `abandon` → `done` + `needs_attention` + `label_attention` + handback + a comment naming the missing tool. It is a configuration fact, true on every poll until somebody installs the binary or declares a `review_skill`, which is `MissingReviewSkillError`'s situation on the other path and now gets the same answer. Before the alpha-53 review it was folded into `:tool_unavailable` and waited fourteen days before ending under `pipeline_watch_expired`, a reason that says the watch stopped moving. A project on the skill path runs its review through `danger-claude`, which is a hard dependency, so nothing is skipped for it |
| An external tool resolving its gems inside autodev's own bundle | Cannot happen any more: `DangerClaudeRunner::CLEAN_ENV` unsets `GEM_HOME` and `GEM_PATH` alongside the `BUNDLE_*` set, so every child of `ProcessRunner#spawn_process` (and of the post-completion spawn, which merges the same hash) resolves as if launched from a terminal. It did happen: autodev is installed in deployment mode with `path: vendor/bundle`, Bundler rewrites those two variables **in the process environment**, and the two were the ones `CLEAN_ENV` did not name — one production review's `dc_stderr` carried a backtrace through `…/autodev/1.0.0-alpha.47/libexec/vendor/bundle/ruby/4.0.0/gems/gitlab-5.1.0/lib/gitlab/request.rb`, i.e. `mr-review` had loaded `gitlab` out of autodev's bundle, and being a `bundler/inline` script it installed its own gems there too — under a Ruby autodev chose, in a directory `brew upgrade autodev` erases (Autodev #77) |
| Project declares `review_skill` but the **branch that decides** (the target branch the merge request under review is going into; the project's `target_branch`, else the repository's default branch, where no merge request exists — the health probe's case) has no matching `.claude/skills/<name>/SKILL.md` nor the flat `.claude/skills/<name>.md` | `MissingReviewSkillError` — a `ConfigError`, so the refusal to fall back to the `mr-review` binary is unchanged (that would run a different process from the one the project declared, silently), but a class `launch_review` can recognise (Autodev #81). It is rescued there and routed to the shared abandon point: `abandon` → `done` + `needs_attention: review_skill_missing` + `label_attention` + ticket handed back to its author + a GitLab comment naming the skill, the repository path that was looked for and, since Autodev #89, the ref it was looked for on. Neither review counter moves — the review never ran, so it neither succeeded nor failed. **Rescued and stopped, never rescued and resumed**: handing the row back to `checking_pipeline` writes an activity row on every poll, which keeps it out of `DormantAudit`'s active arm forever *and* restamps `checking_pipeline_since`, standing the age bound back up — the unbounded, unsignalled loop Autodev #74 preferred to park in `reviewing` rather than create. A give-up has neither property because the row never comes back: `dispatch_pipelines` selects `checking_pipeline`, `dispatch_done_unassigned` excludes flagged rows, and `dispatch_infra_recheck` selects `stagnation_pipeline`. Before Autodev #81 the error escaped `PipelineMonitor#check`'s generic rescue, the row sat in `reviewing` where no pass re-read it, and the only thing that reached a human was `DormantAudit`'s `dormant_exhausted` five hours later — under "this line stopped moving", never under the real cause, which existed and was precise but only in the log. A **bare** `ConfigError` out of the review still escapes, unchanged: nothing on this path knows what it means. |
| Skill review ran but GitLab had not computed the MR's `diff_refs` yet | `review_with_skill` answers `:inconclusive`, not a value on the true/false axis (Autodev #74): `launch_review` sends the row back to `checking_pipeline` via `resume_watch` and touches neither `review_count` nor `review_failure_count`, so the next poll runs the whole review again — and `restore_watch_clock` puts back the `checking_pipeline_since` the poll started with, because `stamp_pipeline_watch!` would otherwise restart the 14-day age bound on every such poll and it could never fire. Deliberately **not** `poll_inconclusive!`: that flag stands the bound down for the cycle, and this poll did read a pipeline status — same ruling as `locked` in Autodev #69 |
| The review's tool could not run — `danger_claude_prompt` raised (the container runtime, a timeout, a crash), or `mr-review` timed out, crashed, or exited non-zero (its *absence* is the row above, `:tool_missing`) | `:tool_unavailable` (Autodev #107), on the same `resume_watch` mechanism as `:inconclusive` above and for the same reason: none of these is a statement on the merge request, so `dispatch_review_outcome` spends neither counter. Measured cause: bobette's Docker engine refused every `danger-claude` call in `ensure_volume` for nine hours (02-03/09/2026) on an API-version mismatch, and burned five `review_failure_count` failures on powerpanne/core#16030 in the middle of it, abandoning a merge request that was `mergeable, conflicts no`. `mr-review` exiting non-zero is included on purpose: the binary posts its own findings to GitLab, so its exit status carries no verdict autodev can read, which is also why the binary path no longer spends the budget on anything but success — its credential sat revoked for four months (Autodev #80) while this counter was the only thing watching and never said so. Bounded by the age bound, `pipeline_watch_max_days`, and by nothing else. A per-cause counter was tried by the first alpha-53 review's remedy and removed by the second: keyed on the failure's message it never counts (git's `after 75002 ms` moves every attempt — Autodev #99's defect), and keyed on a stable one it gives a healthy request up after a ten-minute burst of GitLab 502s. The age bound's own sentence — "watching for N days without ever being able to conclude" — is true of this outcome, which is what makes it the right bound. The distinction between the two causes is **logged and not recorded**: an activity row per poll takes the request out of `Issue.without_activity_since`, which is the clause common to all three of `DormantAudit`'s arms, so for the whole length of an outage the row left the safety net Autodev #103 had just widened — this file's own `launch_review` comment gives that as its reason for not rescuing `ConfigError` and resuming. `WatchBound#log_bound_withheld` is the precedent for logging a per-poll countdown instead. The give-up happens once and does reach the journal and the ticket |
| The skill review's own clone does not complete | `:clone_failed` (Autodev #107), also `resume_watch`, reversing the Autodev #74 fix-round-1 choice to count it as a review failure. A clone failure *can* be request-specific (a deleted source branch) but arrives with no evidence to tell that apart from routine GitLab flakiness — Autodev #96 measured ~9% of GitLab reads failing from bobette by TCP refusal, in bursts. Over-spending the budget on an unreadable cause abandons a healthy request (the powerpanne/core#16030 measurement above); under-spending only costs polls, bounded at `pipeline_watch_max_days`. Same bound as the row above — the pipeline-watch age, log-only per poll. A deleted source branch does fail for ever and for this request alone, but autodev cannot tell that from the routine flakiness it shares its shape with, and the counter that would have ended it sooner proved to cost more than the wait. Positively identifying a deleted source branch — the `MissingTargetBranchError#confirmed?` idiom applied to the source rather than the target — would move it back to the *spending* side for that one cause, and is deliberately out of scope |

## Key Design Decisions

- **Rails 8 monolith over single-file CLI**: The single-file pattern (still used by `danger-claude`, which is pure stdlib, and by `mr-review`, whose `gemfile(true)` is why unsetting `GEM_HOME`/`GEM_PATH` matters — see Error Handling) stopped scaling once we needed background jobs, multi-DB, SSO, and structured background processing. Rails 8 + Solid Queue replaced ~2,000 LOC of bespoke threading/Sinatra/Sequel/poller with conventional Rails primitives. See `docs/railsification-postmortem.md` for the migration's full account.
- **AASM state machine**: Formalized transitions prevent invalid state changes. Guards handle conditional branching. `after_all_transitions :persist_status_change!, :emit_activity_event!` auto-saves and writes a row to `activity_events`.
- **Supervisor over single-process**: `bin/autodev` parent spawns `bin/rails server` + `bin/jobs start` instead of running an in-process Puma + thread pool. Each child boots its own Rails app; SQLite WAL + `busy_timeout` handles the two-writer contention.
- **Multi-DB (primary + queue)**: Solid Queue's 10 tables live in their own SQLite file so their CRUD churn doesn't share the WAL with business writes. AR's multi-database config (`config/database.yml`) handles the routing transparently.
- **Review after pipeline**: the review runs after the first green pipeline, not immediately after MR creation. This ensures the pipeline is stable before review comments are generated.
- **The skill judges, autodev posts** (Autodev #74): a project declaring `review_skill` gets its own review skill run via `danger-claude -p` instead of the `mr-review` binary, but the skill is never allowed to write the review itself. Both PowerPanne's and Fast's review skills state in bold that they write nothing without the developer's explicit go-ahead, and `danger-claude` runs `claude -p` non-interactively — there is nobody at the keyboard to give it. Rather than fight the skill's own discipline, `SkillReviewer` reads it as the contract: the skill stops at its findings, writes them to a JSON file (`ReviewContract`), and `ReviewPublisher` — running as autodev, not as the skill — posts them to the MR. STOP is not an obstacle the harness has to route around; it is the seam the design uses.
- **The branch that decides the review skill is the project's target branch, never the branch under review** (Autodev #89). Two readers ask "does this project carry the review skill it declares": `PipelineMonitor::SkillReviewer`, at review time, and `Autodev::ReviewSkillProbe`, once per poll cycle for the health card. They used to ask about **different branches** and nothing said so — the review looked inside its clone, which is of `issue.branch_name` and, being `git clone --depth 1 --branch <b>`, single-branch; the probe asked GitLab about `target_branch`. Measured on 31/08/2026: 13 of 23 live branches carried no review skill while the probe correctly reported "2 declared, 2 present", and request powerpanne 15842 had already been given up on 28/08 under `review_skill_missing` — a terminal abandon, on a reason whose immediate cause was right and whose reading was false. The ref is now one definition, `ReviewSkillSource` (`lib/autodev/review_skill_source.rb`), and it is a **target** branch and never the branch under review, because a merge request may modify the review skill and must not supply the rules that judge it — the Autodev #79 ruling one layer up. *Which* target is `TargetBranch`'s question, not this module's: the review holds a merge request, so it asks question 2 (the branch that merge request is going into — the review round of the alpha-50 lot corrected #89 on this point, since a merge request cannot modify its own target and #91's rule therefore carries); the probe holds none, so it asks question 1 (the config's `target_branch`, else the repository's default branch). The skill is read off that ref over the API and written into the clone before `SkillsInjector.inject`, as a whole subtree (`tree` + one `file_contents` per blob) because the skill is multi-file and a lone `SKILL.md` would reference files that are not there; `git show origin/<ref>:…` is not available, for the same single-branch reason. The declared skill's directory is dropped from the clone first and unconditionally, so the target's copy wins with no exception. Everything reads through `GitlabHelpers.answer`: an outage is an `ApiUnavailableError` that `launch_review` already returns to `checking_pipeline` and re-raises, never the terminal `MissingReviewSkillError` — which is why the API route needed no new recovery branch. `test/review_and_probe_read_the_same_thing_test.rb` is the pendant of `test/skill_layouts_are_one_definition_test.rb`: the layouts were unified by #81, the ref by #89, and both are derived rather than listed.
- **A resolution is a claim, and it may not be made by the agent that produced the correction** (Autodev #79): resolving an MR discussion *is* the statement that the review point is dealt with, and until #79 the same danger-claude session both corrected and declared. Nothing in between looked at the diff, and the only thing downstream — the pipeline — answers a different question ("do the tests pass"), so a fix aimed at the wrong thing, one that removes the symptom without the cause, or one that changed nothing at all closed its thread exactly like a good one. The correction is now measured per thread (`git diff <the thread's base sha>..HEAD`) and checked against the original finding by a **fresh** `danger-claude -p` answering a two-field contract file. Three deliberate limits make it converge where a re-review would not: the verifier is not the fixing session, it carries no `mr-fixer` agent, and its prompt confines it to *this* finding — the exact asymmetry PowerPanne's own review skill draws when it prescribes verifying each fix after triage and forbids re-running the adversarial pass on the corrected commit. The failure direction is #62's: `addressed` is the good news, so anything short of it — the verdict, an empty diff, a crashed pass, an unreadable contract — leaves the thread open, and the recovery is the loop that already exists (re-read next round, `stagnation_discussions` after `stagnation_threshold` identical rounds). The cost is a setting rather than a surprise: `fix_verification_max` caps how many corrections a round verifies **and therefore how many threads it attempts**, so the bound never buys itself an exception to the invariant. `0` is an opt-out somebody has to write down.
- **Stagnation detection**: Replaces `max_fix_rounds`. SHA256 signatures of failed job names (pipeline) or unresolved discussion IDs (discussions) detect when the same failures repeat consecutively. Configurable threshold (`stagnation_threshold`, default 5). **The budget is spent by an attempt, not by a poll** (Autodev #71): the pipeline signature is written *after* `clone_and_fix` returns, and the discussions one after the round's corrections have been attempted, so a cycle that could not reach the correction leaves the counter where it was. **Counting and checking are not the same act, and conflating them disarmed the discussions guard** (Autodev #99): the pipeline side bails *before* the attempt on the count it already has and writes the new one after, while the discussions side did both inside `finalize_success` — which `run_fix_cycle` only reaches when the round produced commits. A round that changed nothing therefore neither counted nor checked, which is precisely the round the guard exists for: powerpanne 15205 ran eighteen of them over sixteen hours with `count` stuck at 1, exhausting the Claude quota twice. `finalize_no_commits` now goes through the same guard — that round IS a completed attempt, #71's rule is untouched — and a **ceiling** (`MrFixer#fix_round_ceiling`, `stagnation_threshold * 3`) sits above both, read off `issues.discussion_fix_round` before any GitLab call — its own column, because `fix_round` is the sum of the two loops and the ceiling is a sentence about one of them: it is not a second guard of the same kind but the answer to the guard itself being unreachable, and it gives up under its own reason, `fix_rounds_exhausted`, never `stagnation_discussions`. Written before the attempt, an unreachable *issue* endpoint (the prompt-context read #67 made raising) advanced it once per poll with nothing attempted and gave the ticket up on a stagnation that had not happened. The invariant is structural rather than a list of causes: every way out of the attempt that is not a completed one is an exception, and the write is the next statement. The one non-exception it also excludes is a poll flagged `poll_inconclusive!` — an evaluation that never ran; one flag, two bounds (this and the age bound). "The failure is not code-related" is a verdict and does count.
- **One abandon point** (Autodev #60), **and one end label for every give-up** (Autodev #63): every way autodev stops short of a nominal delivery — pipeline stagnation, discussion stagnation, an expired pipeline watch, the review-round limit, since Autodev #66 an MR closed without being merged, and since Autodev #81 a declared review skill missing from the repository (the one give-up that starts from `reviewing`, which is why that state joined the event's sources) — goes through the `abandon` AASM event and `IssueAbandonment#abandon_issue`. Four call sites used to write `status: 'done'` directly, so they emitted no `transition` row (nothing in the activity journal, nothing in the audit log) and skipped the `after_all_transitions` callbacks — which is exactly what left the stale `checking_pipeline_since` clock #53 had to clear by hand at each site. They also disagreed on assignment: one handed the ticket back to its author, three left it on autodev, where nobody sees it. Both are now uniform. *Who* gets it back is `IssueNotifier#handback_target` since Autodev #98, and it is the author in every ordinary case — the exception is a row `ReviewArrearsSweep` took from somebody (GitLab Community holds one assignee, so it cannot join a ticket), which records them in `issues.displaced_assignee_id` and gets it back to them; handing such a ticket to its author would move it to somebody who never had it, and on one of the 20 arrears rows that author is a deactivated account. What is **not** unified is `attention_reason`: `dispatch_infra_recheck` selects `stagnation_pipeline` and re-arms the row, so a give-up that is not a deferral must keep a different reason, and each reason keeps its own GitLab comment. `give_up_reviewing` (`review_failures_exhausted`) still fires its own `review_giveup` event — it is the one give-up that starts from `reviewing`, and it already emitted a transition and already reassigned — but since #63 it poses the same `label_attention` as the others: the end label is a property of "autodev gave up", not of which path got there.

  **The symmetric rule for the resume, since it was missing (Autodev #93/#106).** Every handback this decision describes has to be undone before the row can work again, and two of the three passages that put a handed-back request back to work did not: `PollRouter#resume_recovered_infra` (the infra recheck) and `Issue.reset_for_retry!`'s two operator callers (`IssuesController#reset`, the `--reset` CLI) re-entered `checking_pipeline` with the ticket still assigned to whoever the abandon gave it to, and `dispatch_unassignment` closed the row at the next cycle with a comment blaming that person for something nobody did — observed on powerpanne/core#16030, 03/09/2026. The reclaim (`Autodev::TicketReclaim`, the model `ReviewArrearsSweep#reclaim` already exercised in production) is now shared by all three passages: write the assignment, read it back, record the displaced person, announce it by name. And so is the **question that has to come first** — `Autodev::UntouchedSinceGiveup`, which the sweep had and the infra recheck did not, so that pass took the ticket of anybody who had picked the work back up (alpha-53 review). The operator reset needs no such gate: the human asking for it *is* the answer. `Issue.reset_for_retry!` itself stays a pure database writer with no client — `revive_stalled!` and `recover_on_startup!` call it too, for rows that were never handed back, and must reclaim nothing — so the GitLab half lives in `Autodev::ResetReclaim`, invoked only by the two operator entry points.
- **Polling by assignee**: Issues are discovered by querying GitLab for issues assigned to the autodev user with `labels_todo`, replacing the old `trigger_label`-based approach.
- **3 labels only, plus an optional fourth for a give-up**: `labels_todo`, `label_doing`, `label_done`. Label stays `label_doing` during the entire implementation + pipeline + fix + review cycle, and switches to `label_done` only when reaching `done` **through a nominal delivery**. That sentence was the intent all along and the retry path broke it (Autodev #100): `perform_retry_errored` forked on whether the request carried a merge request and posed `label_done` when it did — but both of its destinations are working states, so it announced the work as finished while autodev carried on, for ten hours on powerpanne 15205. The fork was correct when written, against a five-label config where `label_mr` meant "an MR exists"; that label was later *renamed* `label_done`, taking over a different label's meaning, and the call site kept its method name. Both branches now pose `label_doing` and the fork is gone. `test/retry_resumes_it_does_not_deliver_test.rb` holds the rule as a derived guard: every caller of `apply_label_done` in `lib/` and `app/` must be declared with the delivery it makes, so a new one cannot appear without somebody writing that sentence down. The one interruption is a clarification (Autodev #75): while autodev waits on a human the ticket goes back to a `labels_todo` value, because that is both where `dispatch_new_issues` looks and where the ticket honestly belongs — the work is in the hands of the person who was asked. Which value is not a choice autodev makes: `labels_todo` is a list and both of powerpanne's entries are in live use by different people, so `apply_label_doing` remembers the one it stripped on pickup and `apply_label_todo` puts that one back (first of the list only when the request never carried one). An abandon poses `label_attention` instead (Autodev #63): on the configured projects `label_done` is `Development::Awaiting Feature Review`, so posing it on a give-up announced work as reviewed that nobody had reviewed — 28 tickets landed on the review board that way during the 11/08/2026 incident. `label_attention` is a **setting, not a derived value**: the scope derived from `label_doing` + `label_done` names a scope (`Development` on both projects), not its values, and what lives in it is project taxonomy autodev cannot pick from (powerpanne offers `StandBy` / `Awaiting CR` / `Awaiting Merge`, ff/fast/core only `NeedEstimation`). Unset is a **defined fallback**: no end label at all, the row keeps `label_doing` — a ticket that looks in progress is less wrong than one that looks reviewed — and it costs no GitLab call. Optional but not standalone (rejected without the three required labels; a blank value is rejected rather than read as unset), and `apply_label_doing` / `apply_label_done` clear it, so a re-armed row never carries two values of one GitLab scope.
- **Labels are re-read on every active row, and a handover is scope-derived**: a human who moves the workflow label stops autodev within one poll cycle. "A label autodev does not know" cannot be read literally — real tickets permanently carry out-of-workflow labels (`PM::Evolution`, client names, `Backlog`), so the verdict is confined to the GitLab label *scope* derived from `label_doing` + `label_done` (the two labels autodev owns and writes; `label_attention` is subtracted from the *free-label* set too since #63, but stays out of the derivation so a project spelling it elsewhere cannot disable the rule). `labels_todo` is excluded from the derivation on purpose: it is the human entry point and is often unscoped (`To Do`), so including it would disable the rule. No shared scope → the rule self-disables to "`label_doing` removed / `label_done` applied". Authorship comes from GitLab's resource label events, not from the state machine's expectation, because `apply_label_done` writes the label just before the row reaches `done`, outside the per-issue lock the poll cycle holds — but the events are read **only** once the free label check has a candidate, so a healthy ticket adds no API call. Which is why **clearing autodev's label scope is opt-in** (Autodev #98, corrected on review of the alpha-52 lot): the value a human moved the ticket to *is* the evidence this rule reads, so a write that removes it before the question has been asked destroys the answer. `manage_labels(clear_scope: true)` has exactly one caller — `repose_working_label`, reached only from `ReviewArrearsSweep`, the one path that establishes nobody has touched the row before it writes — and even there it is confined to the labels autodev **owns** (`label_doing` / `label_done` / `label_attention`), never to the scope: both configured projects declare a scoped entry label, so a scope test would wipe a reviewer's column while a request parks in `needs_clarification` waiting on that same reviewer.
- **Post-completion at unassignment**: The `post_completion` hook triggers when autodev is unassigned from a `done` issue (not immediately after pipeline green). Since #52 an *active* row unassigned mid-flight goes to `closed` instead, so it never reaches this hook — the hook is for delivered work, not for work a human interrupted. Since #60 the pass also skips `needs_attention` rows, for the same reason: a `done` row that autodev abandoned is not delivered, and making the reassignment uniform would otherwise have walked all the give-up paths straight into a deploy.
- **`closed` is almost terminal**: the poller skips any `status != 'pending'`, and the one automatic way back is reposing a `labels_todo` label **after** `finished_at` (`PollRouter#reenterable?`). Without that gate #52's stop would be a trap — the GitLab notice it posts tells the reader to repose the todo label and reassign. With it, the dashboard's close button keeps working as an off-switch: there the todo label predates the click, so nothing new was asked. Everything else still reopens only via `#reset`. Which of the four reentry paths a reposed label takes is decided by `ResumeHandler#reenter_destination` from the MR's state: `opened` → the pipeline check (or a full reimplementation when a human left new feedback on the *issue* after the last delivery — bug #32), `merged` → skip, a transient state → **wait** (`locked`, GitLab's mid-merge state; Autodev #67 took it out of the `else`, which cloned and re-implemented over work about to land, and Autodev #72 replaced its hand-written `when 'locked'` with the shared `MrState.transient?`), anything else → reimplementation. What each does with `review_count` is not uniform, and since Autodev #85 not arbitrary either: the reimplementation path resets it to 0 (the branch is being rebuilt), and the pipeline-check path **caps** it at 1 rather than posing 1. Capping is what the line was always for — an inherited value at `MAX_REVIEW_ROUNDS` would send the next green pipeline into `green_branch`'s `:review_limit` short-circuit — but posing it overwrote the 0 of a request no review had ever completed on, and `green_branch` then skipped the review and delivered it under `label_done` (`Development::Awaiting Feature Review`). The same line serves the automatic reentry, `PollRouter#resume_recovered_infra`, whose population is a pipeline stagnation and therefore mostly requests at 0 — and, since Autodev #93/#106, reclaims the assignment before any of this runs, because every row in that population reached `done` through `abandon_issue`'s handback. A read GitLab could not answer is not one of the four: it aborts at `PollRouter#route` and the issue is re-read next cycle. The gate costs one `issue_label_events` call per cycle for every row that is `closed` in the DB while its GitLab issue is still open, assigned and todo-labelled, and that cost is **recurring** for exactly the case it rejects — a dashboard close with the label left on never changes, so it is re-asked forever. Measured at zero rows on the 12/08/2026 production copy (Autodev #60), which is why it is documented rather than bounded.
- **No blocked state, but not an unbounded one**: Canceled pipelines keep the issue in `checking_pipeline` until manual intervention or natural resolution — an interrupted run has no verdict to read (its blocking jobs are `canceled`, not `failed`), and unlike a manual gate it is usually superseded by a new pipeline that `head_pipeline` re-points to. That wait is capped at `pipeline_watch_max_days` (default 14) since Autodev #53, because "indefinitely" meant 29 773 polls on one production ticket — capped, but only on a poll that actually read a pipeline status (Autodev #56): an API error or a Claude-quota deferral ends a poll without concluding anything, and giving a ticket up for that reason is not a cap, it is a false negative nothing re-arms.
- **A failed GitLab read is an abort, not a value** (Autodev #62): `GitlabHelpers.answer(:what) { … }` is the one place a call that did not produce an answer becomes `ApiUnavailableError`, and there is deliberately no variant that returns a fallback. "Did not produce an answer" is `GitlabHelpers::TRANSPORT_ERRORS`, and it is not only HTTP: the review round of the alpha-50 lot found the wrapper converting `Gitlab::Error::ResponseError` alone, so a `Net::ReadTimeout` / `Errno::ECONNRESET` / `OpenSSL::SSL::SSLError` reached `SkillReviewer`'s `rescue StandardError => e; raise ImplementationError` and five network hiccups gave a request up under `review_failures_exhausted`. It now also converts `SystemCallError`, `Timeout::Error`, `SocketError`, `OpenSSL::SSL::SSLError` and `EOFError` — as broad as the block, which wraps a client call and nothing else — while every programming error (`NoMethodError`, `ArgumentError`, `NameError`, `TypeError`) keeps travelling as itself, because reading a bug here as "GitLab is down" is the same lie reversed. **There is a third category, and it is the other half of the same subject** (Autodev #95): a failure where GitLab *did* answer, and the answer is that the request cannot succeed as it is formed. The alpha-50 round widened the family towards the calls that never complete; this narrows the one member that can also mean something else. `GitlabFailure` is where the two are told apart — `answer` owns the rule, that owns the reading — and `GitlabFailure::INVALID_REQUEST_STATUSES` is **400 and 422 only**, with every other code left in the outage family for a reason a reader can check: a 404 is read as a full answer *inside* three blocks and, decisively, is read back off the converted exception by `ReviewSkillSource#confirm_ref!`, which is the one place a 404 becomes `target_branch_missing`; a 401/403 is a property of the credential rather than of the request, which is what `MrReviewTokenProbe` and the health card exist to say; a 429 is a rate limit, where coming back later *is* the answer; and 405/406/409 stay outside as the conservative default, because the failure direction of that list is that a code wrongly called "invalid" can end a request. The resulting `InvalidRequestError` is a **subclass** of `ApiUnavailableError`, for `MissingTargetBranchError`'s reason and not as a convenience: what the parent encodes is "this unit of work cannot conclude", which is exactly the situation, and every boundary therefore keeps behaving correctly with no new rescue clause — a sibling class would land in `PipelineMonitor#check`'s generic `rescue StandardError` on one boundary and in *no* rescue on the other. What it must not inherit is the **waiting**: `describe` is overridden so the line an operator reads names the refusal instead of blaming an outage, and `InvalidRequestBound` gives the request up after `stagnation_threshold` occurrences of the same refusal. Measured 01/09/2026 on powerpanne 15205: a merge request in conflict has no resolvable line codes, so every position `ReviewPublisher` handed GitLab came back 400, read as an outage, returned to the watch spending nothing, and cost another eighteen-minute skill review every poll — close to 90% of a worker thread, with `abandon_expired_watch` unreachable behind the abort. Two answers, not one: the publisher **demotes** a refused position into its summary comment (the same thing it already did with a note GitLab returned unanchored, so a review that produced its findings never loses them), and only a refusal of that fallback too reaches the bound. A third was owed and the first round of the ticket did not pay it (neutral review): demotion says nothing about **delivery**, and `contract.verdict` was read nowhere, so a `changes_requested` review with every finding demoted went out under `label_done` two polls later — the verdict had only ever been held by the discussion threads the findings happened to be anchored on. `SkillReviewer#unanchored_verdict?` is where the verdict now holds it itself, and `review_findings_unanchored` is where such a review stops. No `confirmed?` flag is needed here, which is the one place this differs from #91: `MissingTargetBranchError` was raised both by evidence and by an outage wearing the same exception, whereas an `InvalidRequestError` is only ever built from GitLab's own 400/422 and is therefore evidence by construction. Four readers had answered an API error with a neutral value, and the neutral value is always the good news at these call sites — `[]` unresolved threads is a clean MR (delivered), `[]` failed jobs is a recovered pipeline (re-armed), `nil` jobs is a green `manual` pipeline. The caller cannot tell an outage from a verdict, and every verdict on this path is terminal. Raising gives the failure no representation as data: the unit of work (`PipelineMonitor#check`, `MrFixer#fix`, `recheck_infra_recovery`) ends at its own boundary rescue with the row untouched, and the next poll re-reads. The property that matters for the *next* API call added is that the safe behaviour is now the default — a read written with no rescue at all already aborts correctly, so reproducing the defect takes a deliberate `rescue → value`, and `test/api_failure_is_not_a_verdict_test.rb` fails until that method is declared in one list with the reason its substitute is safe — including when the substitute is an *exception of another class* (`raise ImplementationError, e.message` used to count as a re-raise; Autodev #73). What that guard proves is that every swallow is **declared**, never that a declaration is **true**: the reason is an English sentence nothing verifies, which is how two entries claiming "no read inside" survived a review with an unprotected `client.issue` underneath them. The limit is now written in the file, next to the list. Since Autodev #67 the rule also covers the **prompt context** (`fetch_full_context`), which was the one read on this tree #62 left bare: it sits under the `rescue StandardError` of `attempt_fix` / `execute_fix_cycle`, so its failure was imputed to the correction — `error`, a comment blaming the fix, a retry spent — and it cannot be hoisted out (it needs the clone's work directory, for the ticket's images), so it declares itself with `answer` and both boundaries re-raise. `fetch_full_context` is now all-or-nothing: `fetch_mr_discussions_context`'s `''` and `append_comments`'s "non-fatal" both went, because a prompt silently missing the review history or the ticket's comments reads exactly like a ticket nobody commented on — and bug #32 is the case where the whole instruction lives in such a comment. The **one** exception left is `append_links`, whose rescue answers a capability gap on older GitLab rather than an outage. #67 also extends the rule off the poll tree to the **reentry decision** (`PollRouter::ResumeHandler#reenter_destination` and `GitlabHelpers.human_comment_since?`), where the substitute was `:reimplementation` — a full clone + danger-claude + push on a ticket whose MR may already be merged — with `PollRouter#route` as the boundary, per issue rather than per pass so one unreadable MR does not take the project's whole cycle down. The guard's perimeter is deliberately restricted to code that *acts on a read*, and `test/api_failure_is_not_a_verdict_test.rb` states which files are omitted and why (writes, and the poll passes whose rescue already means "do not act on this row this cycle"). Writes are a separate case and stay as they are (a failed `retry_pipeline` or `resolve_merge_request_discussion` reports what happened, it does not invent a verdict). This deliberately **no longer covers `manual`/`skipped`** (Autodev #51): a manual `deploy_review` is the normal end of a green MR on some projects, so that wait was infinite by construction, and the blocking jobs answer the question the roll-up cannot. Infrastructure failures do the same *only until stagnation* — a recurring infra/deploy failure that never recovers is bailed out via `handle_stagnation` → `abandon_issue` (→ `done` + `needs_attention` + reassignment) after `stagnation_threshold` identical polls, so it can't loop forever.
- **One definition of "this MR state carries no verdict"** (Autodev #72): `MrState::TRANSIENT_STATES` (`lib/autodev/mr_state.rb`) plus the predicate `MrState.transient?`, read by the four places that act on `mr.state` — the pipeline watch (`MrStateChecker#mr_state_concluded?`), the reentry decision (`ResumeHandler#reenter_destination`), the infra recheck (`InfraRecheck#recheck_verdict`) and the `post_completion` hook (`PollDispatcher#mr_state_defers_hook?`). Autodev #69 introduced the allow-list in one place on purpose, but that place was a module of `PipelineMonitor`, so the other three readers could not use it and each answered the question again: #67 wrote `when 'locked' then :wait` by hand (a second copy, free to diverge — the shape #62 removed for `fetch_unresolved_discussions`), the infra recheck tested `== 'opened'` and **spent one of the `infra_recheck_max` attempts** on an answer that meant "wait", and the hook tested `%w[merged closed]` so a `locked` MR counted as neither and let a deploy through while GitLab was merging (latent — no project configures `post_completion`). What is shared is the answer to "is this a verdict", **not** the decision that follows: the four ask different questions (was this delivered, does this need reimplementing, does this need re-arming, does this need deploying) and each keeps its own answer. The population is four, checked: the other `state` readers read an *issue*'s state, and `DeployReviewSearch#related_open_iids` filters candidates for a picker rather than taking a verdict, which is written down where the list lives.
- **One definition of "which branch is this work targeting", and two questions that are not the same one** (Autodev #91): `TargetBranch` (`lib/autodev/target_branch.rb`) plus its `Resolver` mixin's `target_branch_for(work_dir, mr_iid)`, read by the six places that name a base — the rebaser (`RepoRebaser#rebase_branch_on_target`, which now takes a required `base:`), the MR creation, `verify_changes`, the clone command, `MrFixer::FixCycle#run_fix_cycle` and `PipelineMonitor::FailureHandler#prepare_work_dir`. The rule: **a new merge request takes the configuration, a merge request that still carries the work takes the target it carries.** "Still carries the work" and not "exists": `mr_iid` stays set on a request whose merge request a human closed (`ResumeHandler#reenter_via_reimplementation` keeps it), so `MrState.over?` gates the question and a merge request that is merged, closed or gone hands it back to the configuration — which is the right answer, since the run that follows will create a new one. The two questions look alike and are not. "Where do this project's *new* merge requests go" is a property of the project, and `target_branch` in its configuration is the right answer — `create_merge_request` writes that value into the MR, so the two agree at birth. "Where does *this* merge request go" is a property of that merge request, recorded on GitLab, and they diverge the moment the configuration moves under open merge requests. Before this there were three answers and the merge request's own was read by nobody: four call sites wrote `@project_config['target_branch'] || default_branch(work_dir)` by hand, `build_fix_env` answered `default_branch(work_dir)` alone (so the hunk quoted to danger-claude was measured against a base neither the MR nor the config named), and `mr` sat unused in `poll_open_mr`. PowerPanne moved `staging` → `master` on 25/08/2026 with 83 open MRs still targeting `staging`, 64 on autodev branches, `master` 49 commits ahead: a write action on any of them rebased onto `origin/master` and **force-pushed**, while GitLab kept diffing against `staging`. What is shared is the answer, not the decision — same division as `MrState` above: the rebaser decides whether to rebase, `verify_changes` whether anything was produced, the formatter which hunk to quote. `default_branch` lives inside the definition because the repository default is what an *undeclared* `target_branch` means, not an answer of its own. The target is a GitLab read, so it goes through `GitlabHelpers.answer` and never falls back on the configuration (Autodev #67) — that fallback is what would have kept the defect invisible; and a base that is not on the remote after the explicit fetch raises `MissingTargetBranchError` (an `ApiUnavailableError`, so every existing boundary already treats it as "concluded nothing") rather than reading as "already up to date", which is what a missing ref looks like to every git question on this path. That error is **bounded and signalled**, which the review round of the alpha-50 lot had to add: inheriting the family also inherited the waiting, and a deleted branch does not come back, so the row was re-cloned every cycle for ever with all four of the pipeline watch's guard-rails unreachable. `MissingTargetBranchError#confirmed?` separates evidence (`git ls-remote` answering that the remote has no such head, or GitLab describing a merge request that names no target) from an outage wearing the same exception (the fetch did not land, the remote could not be asked) — the second keeps waiting, per Autodev #67 — and on evidence `MissingBaseBound` gives the request up after `stagnation_threshold` occurrences of the same branch under `target_branch_missing`, at `PipelineMonitor#check` and `MrFixer#fix` alike. The counting itself moved to `ConsecutiveOccurrences` when Autodev #95 gave that shape a second bound (`InvalidRequestBound`): what the two share is what "in a row" means — a signature that changes is a different fact and restarts the count — and nothing else, each keeping its own key, threshold, log lines and give-up reason. Nothing here ever writes a merge request's target: retargeting an open MR is a product decision.
- **danger-claude as implementation engine**: Leverages the existing Docker-based Claude CLI wrapper for sandboxed code generation.
- **Solid Queue concurrency control**: `IssueProcessJob`'s `limits_concurrency to: 1, key: "issue-#{path}-#{iid}"` ensures no two jobs touch the same issue at once. Global concurrency cap comes from `queue.yml`'s `threads` setting (`AUTODEV_MAX_WORKERS`, default 3) — mirrors the legacy `max_workers`.

## Localization (i18n)

**Rule: every user-facing string — CLI output, GitLab notes, web UI — must go through `Locales.t` / `t_web`. Never write a literal user-facing string in code or templates, in any language.**

Hardcoded literals are the source of every "why doesn't EN work?" bug we've already paid for once (`Dashboard.status_label` ignored the cookie until 51f0b0e).

### Where templates live

All under `config/locales/`:

| File | Purpose |
|---|---|
| `notifications.{fr,en}.yml` | One-off GitLab issue comments (errors, MR links, completion, stagnation, etc.) |
| `activity.{fr,en}.yml` | Per-issue activity-log entries (the single updated comment) |
| `web.{fr,en}.yml` | Every string rendered by the embedded web UI |
| `cli.{fr,en}.yml` | `bin/autodev`'s boot diagnostics (locale from `web.locale`, default `fr`) |
| `en.yml` | Rails default English (used by gems we depend on) |

Templates are loaded by Rails' i18n railtie. `Locales.t(key, locale:, **vars)` is a thin adapter around `I18n.t` with strict `:fr` fallback (`Locales` includes `I18n::Backend::Fallbacks`). Vocabulary follows `docs/autospec.md` §I — business-facing language, not technical step names.

### How to add a new string

1. Pick a key with the right prefix: `notify_*`, `activity_*`, `web_*`, `cli_*`. Keep them flat (no nesting). A new thematic file also has to be added to `Locales::LOCALE_FILES_GLOB`, or `Locales.t` won't see it outside the Rails process (and the FR/EN parity test won't cover it).
2. Add it to the matching `config/locales/<area>.{fr,en}.yml` files **in both `fr` and `en`**, with the same `%{var}` placeholders in each.
3. Use the right helper at the call site:
   - **Ruby code (CLI, processors, services)**: `Locales.t(:my_key, locale: <locale>, **vars)`. The `locale` argument is mandatory in this layer — pick from `issue.locale`, a config field, or default to `:fr`.
   - **Phlex views**: `t_web(:my_key, **vars)` (auto-escaped, no `h()` wrapper needed). `t_web` resolves the active locale automatically (cookie > config > default).
4. If the string represents a status label or any web concept derived from a Ruby value (not a literal in the template), wire it into `STATUS_LABEL_KEYS` in `app/helpers/web/i18n_helpers.rb` rather than inlining a `case`.

### Locale resolution per layer

| Layer | Source | Helper |
|---|---|---|
| Web UI | cookie `locale` > config `web.locale` > `:fr` | `Web::I18nHelpers#web_locale` + `t_web` |
| GitLab activity log / notifications | `issue.locale` column (per-issue, set on creation, default `:fr`) | `Locales.t(..., locale: issue.locale.to_sym)` |
| CLI dashboard / `--status` / `--errors` | `:fr` for now (no flag) | `Locales.t(..., locale: :fr)` — still go through it so adding `--locale en` later is a one-line change |
| `bin/autodev` boot diagnostics | config `web.locale` > `:fr` | `Locales.t(..., locale: cli_locale(config))` (`bin/autodev`) |

### What NOT to do

- Hardcode user-visible literals in Phlex views. The only allowed bare strings are pure structural markup, code/paths/URLs, punctuation, and technical tokens that aren't translated (e.g. AASM state names, `JSON`, `MR`).
- Translate FR but skip EN (or vice versa). Both keys must exist or `Locales.t` falls back silently and you get mixed-language output.
- Add a *derived* key without adding it to both tables. `test/locales_test.rb` only checks the two tables against each other, so a key missing from **both** satisfies parity and `Locales.t` then renders the key's own name — which shipped twice (`activity_mr_closed` on the GitLab thread of every merged MR, `web_event_abandon` in the `/issues/:id` timeline). `test/i18n_derived_keys_test.rb` is the other half (Autodev #68): it derives the expected key set from the code — the AASM events, the symbols passed to `log_activity` / `notify_localized` / `abandon_issue`, the `attention_reason` values and their three sinks, `ActivityEvent::KINDS`, `HealthReport::CHECKS`, `LabelHandover::EXPECTED_ACTION`, the project config columns — and also checks every key literally spelled out in `lib/`, `app/` and `bin/autodev`. Nothing in it is a hand-maintained list: a *new symbol* in an existing family is covered for free, and a **new derived-key shape** (a call site taking its key from a variable, or a new `:"prefix_#{…}"`) fails until it is declared there with the enumeration that covers it. Autodev #73 closed three ways round it, each verified by injection: an interpolated key is now read whatever its stem (the five prefixes were the ones somebody had thought of, and a notification key has no prefix at all), a key handed straight to `Locales.t` is read off the call site like the rest (four were live and checked by nothing), and a declaration that no longer matches a call site is reported as stale. Same limit as the #62 guard, and stated in the file: it proves every shape is declared, not that any declaration is true.
- Add a new helper that returns French verbatim (e.g. `def label_for_X; 'Terminée'; end`). If the helper produces text shown to a user, it must take a locale and call `Locales.t`.

## Tests

`bundle exec rake test` runs the full minitest suite. `test/test_helper.rb` boots the Rails environment in `RAILS_ENV=test` (in-memory SQLite for both primary + queue) and force-loads the AR models so tests that don't transitively reference them through `Issue` still see them defined. ~452 tests at v1.0.0-alpha.3.

`test/database_test_helper.rb` re-runs the migrations idempotently and wipes `issues` + `activity_events` between tests (`:memory:` SQLite drops the schema on every reconnect; the migration's `if_not_exists: true` makes the re-run a no-op once tables exist).

**Every test file must pass run on its own** (`bundle exec ruby -Itest test/…_test.rb`), not only under `rake test`. A file that passes in the suite and fails alone is the signature of a constant that some *other* file loaded first, and it is a failure mode the full suite cannot see — which is why `lib/autodev` is now required unconditionally by `config/initializers/load_autodev_config.rb`, above the `AUTODEV_SKIP_LEGACY` guard (Autodev #64). That flag gates one thing only: the `Web.config = Config.load({})` disk read of `~/.autodev/config.yml`. **Never add a `require 'autodev/…'` to `test/rails_helper.rb`** — the whole tree is already loaded, and nine such requires were what #64 removed. `test/rails_lib_loading_test.rb` asserts the constant set (derived from `lib/autodev.rb`'s require graph, not listed) and `test/module_load_test.rb` asserts each file loads without raising.

Job tests under `test/jobs/` use `Autodev::JobLogger` mocks; they don't require the full legacy stack.
