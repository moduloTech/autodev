# Changelog

## [Unreleased]

### Fixed

- **`/healthz` no longer walks the migration directories on every request (Autodev #60, item 3).** `HealthReport#check_migrations` (added by Autodev #55) calls `Autodev::MigrationStatus.pending`, which is a set difference between two halves: the versions parsed from the files under `db/migrate` + `db/queue_migrate`, and the versions recorded in `schema_migrations`. Only the second half can change while the process runs. The first was re-walked from the filesystem on every call — two directory traversals per hit on the one endpoint designed to be polled by an external probe. The file half is now memoised per process, keyed on the resolved migration paths and guarded by a mutex (the call happens inside a Puma request thread). `schema_migrations` is still re-read every time, so a migration applied by hand while autodev runs is still seen: a cached *verdict* would have been the real bug.

- **`PollRouter#reenterable?` no longer claims its API cost is transient (Autodev #60, item 4).** Documentation only, no behaviour change. The gate spends one `issue_label_events` call per cycle on every row that is `closed` in the DB while its GitLab issue is still open, assigned to autodev and todo-labelled. The comment said that population "empties itself"; it does not, for exactly the case the gate exists to reject — a ticket closed from the dashboard with the todo label left in place has a label event that predates `finished_at` forever, so the question is re-asked, and answered no, every poll interval indefinitely. Measured on the 12/08/2026 production copy: 60 `closed` rows, none of them still open + todo-labelled on GitLab, i.e. **zero recurring calls today**. Hence the cost is now stated honestly in the code rather than bounded — a cache would buy complexity for an empty set. Re-measure before adding one.

- **A queued job no longer replays the side effects of a transition that did not happen (Autodev #61).** The queue is not a snapshot: `dispatch_pipelines` enqueues the whole `checking_pipeline` population every cycle, so any job outliving the poll interval leaves duplicates behind it — and once alpha.47's `manual`-pipeline resolution turned that job from a millisecond no-op into a full mr-review run, that became the normal case. The state machine did not stop the duplicates. `whiny_transitions: false` makes an impossible transition a silent no-op rather than a raise, and the callers treat the event as a command that always succeeds: `green_first_review` calls `launch_review` after a `pipeline_green!` that did nothing, and `give_up_reviewing` re-applies `label_done`, reassigns the author and posts a GitLab comment after a `review_giveup!` that did nothing. In production on 11/08/2026 that put **486 comments on 28 powerpanne tickets in two hours** — issue #15839 alone took 26 identical "mr-review failed 5 times" comments, one every 105 seconds, every one of them after its last real transition, while its `review_failure_count` climbed to 30 for 5 real rounds. `IssueProcessJob#perform` now checks the row against `DISPATCHED_FROM`, the state each action's dispatch pass selects on, and logs a skip instead of running. One declaration covers all seven actions; the row was being read anyway, so it costs no query. This is not a substitute for `limits_concurrency` — that answers "is another job touching this row", this answers "does the work this job was queued for still need doing".

## [1.0.0-alpha.47] - 2026-08-11

### Fixed

- **The documented "give it back to autodev" gesture no longer parks a ticket for good (Autodev #52).** GitLab allows one label per scope, so on a project whose todo label sits in the workflow scope — ff/fast/core configures `labels_todo: ["Development::ToDo"]` against `label_doing: "Development::Doing"`, and powerpanne/core carries both `To do` and `Development::ToDo` — reposing the todo label on an **active** row makes GitLab drop `label_doing` in the same edit. `LabelHandover#suspect` read that absence as `doing_removed`, closed the row, and posted a comment telling the reader to repose the todo label and reassign — which they had just done. `PollRouter#todo_reapplied_after?` then refused the reentry it gates, because it wants the todo applied *after* `finished_at` and this one preceded it: the ticket sat in `closed` until somebody removed and re-applied the label by hand. `doing_removed` is the weakest of the three signals — an absence, not an edit naming a destination — so it now yields whenever a todo label is present on the row: somebody asking for work is never a reason to stop, and the absence is left to `PollRouter` to read. The two positive signals (`done_added`, `workflow_moved`) are untouched.
- **An operator reset is no longer undone at the next poll (Autodev #53).** `PollTracker#seed_watch_clock` only fills a NULL `checking_pipeline_since`, so the two `update_all` entries into `checking_pipeline` have to *arrive* at NULL — and they did not clear the column, they inherited whatever the row was carrying. Not every exit from the state clears it either: `handle_stagnation` writes `status: 'done'` directly, so the AASM callback that owns the column never runs and the row keeps the clock of the watch that just ended. A ticket bailed out by stagnation months ago therefore came back from **Réinitialiser** with a months-old clock, and the new age bound abandoned it at the very next poll — back to `done` + `pipeline_watch_expired`, plus a `label_done` write and a GitLab comment, silently undoing the operator's action. `reset_for_retry!` and `revive_stalled!` now clear the column explicitly (closing every careless-exit path at once), and `handle_stagnation` clears it on the way out, mirroring the `give_up_on_watch` it is modelled on.
- **The active sweep runs before anything is enqueued (Autodev #52).** `dispatch_existing` ran `dispatch_pipelines` first, and `IssueProcessJob#perform` reloads the row without re-checking the status it was enqueued for — so with Solid Queue picking the job up immediately, the worker won the race against the inline sweep almost every time. That cost #52 its most common case: a pipeline resolving on the same cycle as a handover drove the row to `done` through `handle_green`, `done` is not in `ACTIVE_STATUSES` so the sweep never looked at it again, and `apply_label_done` overwrote the workflow label the human had just set (GitLab dropping `Development::Awaiting CR` to make room). `dispatch_unassignment` — the pass that decides whether a row is still ours at all — now runs first. Pass order was already load-bearing in this method; this makes it so for one more reason.
- **A pipeline watch is now bounded in time (Autodev #53).** Nothing stopped one. `dispatch_pipelines` re-enqueues every `checking_pipeline` row on every cycle with no condition beyond the status, and the only existing bound — stagnation — is fed exclusively from the red branch: `update_stagnation_signature(_, :pipeline, _)` is called only from `infra_skip?` and `check_stagnation_and_fix`, both under `when 'failed'`. A pipeline that is never red — `manual`, `canceled`, `skipped`, or a head pipeline stuck at `created` — therefore accumulated no signature, `bail_on_stagnation?` was unreachable for it, and the row polled forever; `CLAUDE.md` said so out loud ("indefinitely"). Production issue #15894 polled 29 773 times. A poll that ends **without a transition** on a watch older than the new `pipeline_watch_max_days` (default 14, `0` disables) now gives the ticket up: `done` + `needs_attention` with a dedicated `pipeline_watch_expired` reason, `label_done`, and a localised GitLab comment (FR + EN) saying the MR stays open and a human should take it from here. The check is the last statement of the poll and runs only while the row is still `checking_pipeline`, so "the poll ended without a transition" is a condition rather than an enumeration of the branches that go nowhere — a green pipeline on day 15 still completes, a red one still enters the fix cycle, a GitLab outage raises before reaching it, and the branches Autodev #51 is rewriting are covered without naming any of them. The reason is deliberately not `stagnation_pipeline`: `dispatch_infra_recheck` selects exactly that value and would re-arm the row. Clock: a new `issues.checking_pipeline_since`, written by a single AASM callback (so "reset on any transition" needs no clear at each of the six exits) and seeded by `PollTracker` for the rows that arrive through `update_all` — `reset_for_retry!` and `revive_stalled!` bypass the state machine. The migration backfills rows already in the state from their newest `transition` event, falling back to `issues.created_at`, so the bound applies to the existing backlog instead of granting it a fresh two weeks at the release. Why 14 days: above the longest legitimate human absence (a two-week holiday, a shutdown week with a weekend either side), far below the six-week horizon the ticket calls "no longer worth watching", and far above the bounds that already cover the diagnosable cases (~25 min for a red loop at `stagnation_threshold`, ~5 h for `infra_recheck_max × backoff`) — a safety net must only fire on what the specific mechanisms cannot see.
- **A poll no longer writes an `activity_events` row (Autodev #53).** `replace_pattern:` has always meant "this entry supersedes its previous occurrence", but only the GitLab note obeyed it: `persist_event!` ran first and always INSERTed. Production carried **477 827 `pipeline_checking` rows out of 898 424 (53 %)** in a 264 MB SQLite file, 29 773 of them on issue #15894 alone — enough that `/issues/15894` showed 200 poll lines and nothing else, that its GitLab thread was unreadable, that the "Activité de la semaine" sparkline measured polling rather than work, and that `/stream` got one Turbo frame per poll per watched row. One rule now covers both sinks: a replaced note line has a replaced row, which also fixes `pipeline_red`, `pipeline_infra` and `pipeline_evaluating` (the other three `replace_pattern` call sites, which grow the same way on a red-stuck ticket). **What this does to Autodev #50's invariant: nothing, by construction.** Supersession is an `update_columns` that moves `created_at` forward — for a collapsed row that means "last occurrence", the same thing the note line's leading timestamp means — so a row polled last cycle still carries an event from last cycle and `Issue.without_activity_since` reads unchanged inputs. Logging only on pipeline-status change was rejected for exactly that reason: it would have made correctness rest on `checking_pipeline` being absent from `Issue::STALLED_STATES`, a constant defined in another file for another purpose. That absence is nonetheless pinned by a new guard test (against `STALLED_STATES` and both halves of `HealthReport`'s stuck card, plus an end-to-end check that `DormantAudit#candidates` ignores a watched row silent for a week), so a future change to it fails loudly rather than letting the audit reposition a row a live worker holds. Skipping `after_create_commit` is the second intended effect: a re-occurrence pushes no SSE frame.
- **The 477 827 accumulated rows get a purge, as code (Autodev #53).** New `bin/rails autodev:compact_activity_events` applies the collapse retroactively — keep the newest occurrence of a collapsible key per issue, delete the superseded ones — which makes it idempotent by construction, leaves the current "still watching since X" line in place, and touches nothing else (`transition`, `heartbeat`, the system rows and every other `danger_claude` key survive). It reports and deletes nothing unless `APPLY=1`; `VACUUM=1` is a second opt-in because reclaiming the file needs free disk equal to its size and an exclusive lock. A rake task rather than a migration: `auto_migrate` runs migrations at boot in three processes, a 478 000-row DELETE plus a VACUUM must not happen on a schedule nobody chose, and VACUUM cannot run inside the transaction AR wraps a migration in. **It has not been run against any real database** — the production purge is a manual operation and its procedure (dry run, backup, delete, VACUUM, verification queries) is in the design spec. New tests: `activity_logger_collapse_test.rb`, `pipeline_watch_invariant_test.rb`, `pipeline_watch_bound_test.rb`, `models/checking_pipeline_since_test.rb`, `migrations/backfill_checking_pipeline_since_test.rb`, `tasks/compact_activity_events_test.rb`. Design: `docs/superpowers/specs/2026-08-11-bound-pipeline-watch-design.md`.
- **A human can now stop autodev by moving the ticket's workflow label, and autodev notices within one poll cycle (Autodev #52).** Autodev never re-read a ticket's labels, so a human taking the work back had no way of saying so. On `powerpanne/core#15894` the workflow label went from `Development::Doing` to `Development::Awaiting CR` on 24/07 at 09:24, one minute after a "test sur review ok" comment — and autodev kept polling that MR's pipeline for more than two weeks; `#16237`, `#16258` and `#16341` are the same story. `dispatch_unassignment` already fetched each active row's GitLab issue and threw the `labels` array away, exactly as it used to throw `state` away before #44, so the check rides along on the read that already happens. Three edits stop the work: `label_doing` removed, `label_done` applied, or the ticket moved to another label in autodev's own workflow scope. **The scope is derived, not configured**, from `label_doing` + `label_done` — the two labels autodev owns and writes. A literal "a label autodev does not know" rule is unusable: real tickets permanently carry `PM::Evolution`, `Fourrière`, client names, `Backlog`, and that rule would close every ticket on the project. `labels_todo` is deliberately left out of the derivation and merely exempted from the verdict: it is the entry point a human uses, and on `powerpanne/core` it is GitLab's stock unscoped `To Do` while the other two are `Development::…`, so including it (as first proposed) would have disabled the rule on the very project the bug came from. When the two do not share a scope the rule **self-disables** down to the two presence checks, so a project that does not follow the convention gets the documented fallback with no false-close risk and nothing to configure either way. New `Autodev::LabelHandover` (`app/services/autodev/label_handover.rb`), new `test/label_handover_test.rb` (19 cases). Design: `docs/superpowers/specs/2026-08-11-reread-labels-and-assignment-design.md`.
- **Autodev's own label writes are told apart from a human's by reading GitLab's resource label events, at no cost on a healthy ticket (Autodev #52).** Autodev applies and removes these very labels in normal operation, so "by somebody else" has to be established rather than assumed. Inferring it from the state machine's expectation — while a row is active, autodev holds `label_doing` and has not applied `label_done`, so any deviation is somebody else's — is free but races: `apply_label_done` writes the GitLab label a few hundred milliseconds before the row's status reaches `done`, from inside the per-issue `limits_concurrency` lock the poll cycle does not hold, so a sweep landing in that gap would close a ticket autodev was about to deliver and post a comment blaming a human who did nothing. Authorship is therefore read from `client.issue_label_events`, but **staged**: stage 1 works off the labels already in the issue payload and produces no candidate on a healthy ticket, and only a candidate spends the extra call — once, for a row that is closed at the end of the same cycle. Reading the events unconditionally, as the ticket costed it, would have been one extra call per active row per cycle forever (~240/hour at current volume). Both cost claims are pinned by tests, because the two-stage shape is easy to collapse back into one call by accident. Everything unknown resolves to "do not stop" — no event, no matching event, an action contradicting the suspicion, an author that is autodev, or a GitLab error: a missed handover costs what the bug already costs today, a wrong stop kills live work.
- **A ticket autodev was unassigned from is now `closed` and says so on GitLab (Autodev #52).** `stop_unassigned` wrote `done` and left nothing but one line appended to the folded activity note, so the person who unassigned autodev never learned whether it had actually stopped. `done` was also the wrong word: a ticket a human pulled back mid-implementation was never delivered, and #44 had already settled that `closed` says more than `done` for the sibling case of a GitLab closure. The row now goes through the same `close!` + `finished_at` + `needs_attention`-cleanup writer as `close_externally` (new shared `ExternalState#close_row!`, so the two terminal outcomes cannot drift apart), and a real GitLab comment goes out first — through the `unassigned_stop` template that had been sitting in `notifications.{fr,en}.yml` **with no call site** since the pre-Rails poller, reworked with a `done_nominal`-style hand-back line. **One consequence is deliberate:** `dispatch_done_unassigned` selects `done` rows with an open MR that autodev is no longer assigned to, so a row stopped mid-flight used to land in it and fire the `post_completion` hook over a half-finished MR one cycle later (verified against the pre-change code). It no longer does — the hook is a delivery hook. The population it exists for is untouched and is pinned by new `test/post_completion_after_unassignment_test.rb`: every nominal completion path reaches `done` *before* `reassign_to_author` hands the ticket back, and `dispatch_unassignment` only sweeps active rows, so a delivered ticket is still `done` and still unassigned when the next cycle looks at it. Six new locale keys in `fr` and `en`.
- **A stopped ticket can be handed back to autodev the documented way, from `closed` (Autodev #52).** `closed` was terminal — `PollRouter#route_by_state` re-entered from `done` and from nothing else — so moving the unassignment stop to `closed` would have turned the loop every guide describes ("repose the todo label, reassign autodev", after a KO test or a KO code review) into a dead end, and made the GitLab notice the stop posts a lie. `reenter` and `reenter_to_check_pipeline` now also accept `closed`, **gated on a threshold**: only a `labels_todo` label applied *after* `finished_at` counts. That gate is what keeps the dashboard's *Clôturer* button an off-switch — there the todo label was already on the ticket when the operator clicked, so its `add` event predates the close and the row stays closed — while a human reposing the label after autodev stopped produces a fresh `add` and re-enters. The question it asks is the honest one: did somebody ask again *after* we stopped? It costs one `issue_label_events` call per `closed`-but-still-todo-labelled row per cycle, a population that empties itself (a reentry leaves `closed`; the merged-MR branch strips the label), and a `done` row pays nothing. New cases in `test/poll_router_reenter_test.rb`.
- **The dormant audit no longer re-arms a ticket a human has already moved on (Autodev #52).** `DormantAudit#route` gains the same label check, between "unassigned" and "revived", so the ordering stays closure > unassignment > handover > re-arming. This is #48's lesson applied rather than re-learned: a decision about whether a ticket is still ours must not live in one pass while the other population is never swept. Without it, a dormant row carrying `Development::Awaiting CR` would be handed a fresh retry budget and restart work that is no longer autodev's.
- **A ticket being worked on can no longer be repositioned under the worker handling it (Autodev #50).** `dispatch_dormant_audit`'s active arm treats "no `activity_events` row for `stuck_active_after` (2 h)" as "the worker died", and mutates by `update_all` from the poll cycle — outside the `limits_concurrency` that serialises `IssueProcessJob`. That was already false at default settings: `PipelineFixer` emits `:pipeline_fixing` once on entering the state, then loops over the N failed jobs with **two** danger-claude calls each and no activity event in between, so silence in `fixing_pipeline` reaches `N × 2 × dc_timeout` — two slow jobs already reach the window and three exceed it, and a closure or unassignment landing inside it can leave an MR the row no longer records, silently, since the model runs `whiny_transitions: false`. Every **issue-scoped** danger-claude call now writes a liveness row (new `activity_events` kind `heartbeat`, DB-only — no GitLab round-trip) from `DangerClaudeRunner`, the single point both `danger_claude_prompt` and `danger_claude_commit` funnel through, bounding silence to one call in every loop, including ones not yet written. Two call sites bypass `DangerClaudeRunner` entirely (`Autospec::ProjectBriefer`, `Autodev::UsageChecker`) — harmless today since neither is issue-scoped, but named so a future issue-scoped call in their style isn't assumed covered. The rows are invisible to the UI (new `ActivityEvent.user_visible` scope, applied to the issue timeline, the dashboard sparkline, and an SSE guard) and deliberately **counted** by `Issue.without_activity_since`, which is the whole mechanism. `mr-review` — run via `Open3` with no timeout, in the `reviewing` state — gets the same heartbeat immediately before its call, at both its call sites, bounding that state's silence to one review run instead of leaving it unbounded (not a fixed duration: that run's own duration was still unbounded at this point — closed by the Autodev #54 entry below).
- **`HealthReport#stuck_active_after` is now derived instead of only configured (Autodev #50).** It is `max(configured, TIMEOUT_SLACK_FACTOR × the longest configured timeout)` — over `dc_timeout` **and** `post_completion_timeout` (whose shell command gets no heartbeat, so its silence equals its timeout exactly), across `projects` rows and not-yet-imported YAML entries — so raising a per-project timeout widens the window instead of breaking the invariant, and the two settings can no longer be configured into disagreement. Nothing changes at default settings (2 × 1 800 is under the 7 200 s floor); an explicit `monitoring.stuck_active_after_seconds` becomes a floor rather than a ceiling, and the effective value is reported as `window_seconds` on the `stuck_issues` check. The constant is named `TIMEOUT_SLACK_FACTOR`, not `HEARTBEAT_FACTOR` — it multiplies a timeout, not a heartbeat interval, and is a heuristic rather than a bound for as long as any inter-call work (screenshot uploads, `job_trace` fetches, git operations) stays untimed. The same fix makes the "Issues bloquées" card catch long-but-live runs it used to flag — though its meaning shifted alongside it: it now reads "no danger-claude call started", not "no business activity", so a wedged-but-chatty worker (no such loop exists in the codebase today) sits outside what it can see.
- **`post_completion_timeout`'s baked default moves out of a literal (Autodev #50).** The `|| 300` in `lib/autodev/pipeline_monitor/post_completion.rb` becomes `Config::POST_COMPLETION_TIMEOUT`, read by both the runtime and the `stuck_active_after` formula, so the two can no longer drift. New tests: `activity_event_heartbeat_test.rb`, `danger_claude_runner_heartbeat_test.rb`, `pipeline_monitor_review_heartbeat_test.rb`, `controllers/issues_controller_heartbeat_test.rb`, `services/health_report_stuck_window_test.rb`, plus a widened-window regression pair in `dormant_audit_selection_test.rb` and a sparkline exclusion in `weekly_activity_counts_test.rb`. Design: `docs/superpowers/specs/2026-08-10-live-worker-silence-invariant-design.md`.
- **A review that never returns can no longer leave a ticket exposed (Autodev #54).** `mr-review` ran via a raw `Open3.capture3` with **no timeout**, in the `reviewing` state — which is in `Issue::STALLED_STATES`, so `dispatch_dormant_audit` repositions rows out of it with `update_all`, outside the per-issue concurrency lock. #50 bounded that silence at one `mr-review` run by writing a heartbeat before the call, but a wedged run (process hung, pipe never closed) was still unbounded, and no configured value sized the stuck-window for it — `reviewing` was recorded as the one exception the derived window could not reach. It now runs under `ProcessRunner#run_with_timeout`, capped by a new per-project `mr_review_timeout` (baked default 3600 s, sized on 317 production reviews whose longest successful run took 2641 s) — `run_with_timeout` gained an additive `timeout:` kwarg, and `dc_timeout` no longer caps `mr-review` at all. `HealthReport#longest_worker_timeout` **gains the term** (across the baked default, `projects` rows and YAML entries): window-neutral at the default, since `2 × 3600` is exactly the existing 7200 s floor, but a project raising its review cap now widens the window automatically — and the state leaves the exceptions list, `running_post_completion` now the only one remaining. A timeout stays **non-fatal**, as before: the wrapper raises, `Reviewer#execute_mr_review`'s existing rescue answers `false`, and `launch_review` counts a review failure (`review_failure_count`, threshold 5) rather than dropping the request to `error` — behaviour that already held and is now pinned by tests, alongside assertions that the call is wrapped at all and that its working directory stays the process's own cwd (which `Open3.capture3` inherited implicitly). Relatedly, `IssueProcessor::MrManager`'s `run_review` / `execute_review` / `command_exists?` — a parallel review path with no caller anywhere, duplicating `Reviewer` — was deleted rather than kept in sync; `PipelineMonitor::Reviewer` is now the only review path, which it already was in practice.
- **A failed `mr-review` now says why, instead of logging an empty line (Autodev #49).** The call kept `stderr` and threw `stdout` away — and `mr-review` fails writing nothing to `stderr`, so across every retained production log the message is identical and useless: `mr-review failed (non-fatal):` followed by nothing, **15 times, with no exception**. Those 15 are `5 × 3`: three tickets exhausted `REVIEW_FAILURE_THRESHOLD` on them and were delivered with **no review at all** (`#16415`/`!11343`, `#16224`/`!11187`, `#12852`/`!11286`), and the cause is *still* unknown, because the only copy of it was discarded at the call site. Each attempt took ≈1 s once `execute_mr_review`'s 15 s pre-sleep is subtracted — a crash at startup or a rejected argument, not the wedge #54 was about. The failure message now reports **both streams**, each labelled and each rendered `(empty)` rather than as a dangling colon, capped at 2000 characters per stream (up from 300) with the number of dropped characters stated instead of the cut being silent, and the whole thing passed through `Redactor` — the logger on this path in production is `Autodev::JobLogger`, which unlike `AppLogger` does **not** scrub, and `mr-review` holds the same GitLab PAT autodev does. It also reports the **exit status**, which required `ProcessRunner#run_with_timeout` to hand back the `Process::Status` as a fourth, optional element (surplus on a three-variable destructuring, so both `danger-claude` callers are untouched — pinned by a test, along with the first real-subprocess test in the suite): on the one failure shape actually observed, where neither stream says anything, the status *is* the diagnostic, and `exit 127`, `exit 1` and a termsig are three different investigations. Finally, `give_up_reviewing` now persists `@dc_stdout` / `@dc_stderr` onto the row, in the same `issues` columns every other failure in the product uses, so the diagnostic outlives log rotation (no view renders them for a `done` row yet — surfacing them is a follow-up; losing them was not recoverable). **`REVIEW_FAILURE_THRESHOLD` is deliberately left at 5**: all 15 attempts failed deterministically from the first, so no threshold value would have saved those three MRs, and picking a new number against no data is the mistake #54 already made and corrected. What is genuinely missing is aggregation — `review_failure_count` is per-issue, so a globally broken `mr-review` costs 5 rounds *per ticket* and raises N unrelated flags instead of one alert saying the tool is down; recorded as the follow-up, with its threshold and window to be chosen against production numbers. Design: `docs/superpowers/specs/2026-08-11-mr-review-diagnostic-capture-design.md`.
- **A migration that fails to apply can no longer leave autodev running in silent total outage (Autodev #55).** `config/initializers/auto_migrate.rb` rescued every `StandardError` from the migration pass and answered with one `Rails.logger.warn`, so "the peer that won the boot race got there first" and "nobody applied this and the schema is now incomplete" read identically in the log. The first is expected — SQLite reports `supports_advisory_locks? == false`, so Rails does not serialise the two migrators the supervisor produces, and the loser fails on `duplicate column name` or on the UNIQUE insert into `schema_migrations` while the winner's column is already there. The second is a **total processing outage**: `Project#to_project_config` calls `public_send` for every config column, so one missing column raises `NoMethodError` on every job, for every ticket, announced by a single log line. Nothing of the sort has been observed in production — it needs an external writer to hold the SQLite write lock through the whole 30 s `busy_timeout` during a restart — but the blast radius is total, which is what made it worth hardening. The fix splits one `rescue` into two independent questions, in a new `Autodev::MigrationStatus`. **Classification** (`benign_race?`) is a heuristic over the exception message and picks only a log level: `warn` for a recognised race, `error` otherwise, the error branch naming the versions actually left unapplied and pointing at `/admin/health` — and saying so explicitly when a failed pass turns out to have left a complete schema anyway. **Verification** (`pending`) is the migration files minus the `schema_migrations` rows, per database, read through each pool's own connection (`ActiveRecord::Base`, `SolidQueue::Record`) with no `establish_connection`; it is the only predicate that gates anything, so no misclassification can either abort a boot or hide an incomplete schema. `bin/autodev` gates on it: it already played the pass first and alone (it requires `config/environment` long before `run_supervisor`), and now **refuses to spawn its children** when anything is left unapplied, with a `Config error:` naming the database, the versions and the two ways out. That refusal is deliberately confined to the supervisor — the path that starts the workers. `--status` / `--errors` / `--reset` exit before the gate, and `bin/rails runner`, a standalone `bin/rails server` and the test suite never reach it: those are the tools needed to diagnose the condition being gated. For them, a new **Migrations** card on `/admin/health` reports it (`down`, so `/healthz` answers 503 and an external probe pages, with the unapplied versions in `meta`). - **A finished ticket whose pipeline ends on a manual job is now delivered instead of watched forever (Autodev #51).** GitLab reports `manual` when every job that could run has run and what is left needs a human to press play. `PipelineMonitor#dispatch_status` knew three outcomes — running, `success`, `failed` — so `manual` landed in the `else`, which logs a line and returns; the row stayed in `checking_pipeline` and **nothing bounded the wait**, since stagnation detection is fed from `handle_red` only. On a project whose MR pipelines end with a manual `deploy_review`, `manual` is the *normal* end state of a green MR, so every ticket whose MR went green parked permanently. Measured on `powerpanne/core` on 2026-08-10: pipeline 215229 (MR !11154) had all four blocking jobs green and was read **12 729 times in 18 days**, once every two minutes; four tickets (#15894, #16237, #16258, #16341) sat finished with `review_count` 0 — never reviewed, never `label_done`, never reassigned — until three different humans relabelled them by hand, between a day and four weeks later. The same #15894 had already spent 13 days in that `else` on `canceled` before it. The verdict now comes off the **jobs** rather than the roll-up, which cannot express "what gates the merge is green, what gates a deploy awaits a human": the blocking subset excludes `allow_failure: true` jobs (GitLab itself says the result does not count) and unplayed `manual` gates (no result, and never one without a human), and the question asked of it is *did anything that counts fail?* — not *did everything succeed?*, because a blocking job may legitimately sit `created` or `skipped` downstream of the gate and demanding `success` would rebuild the same infinite wait one level down. Nothing can be mid-run: a running job would make the roll-up `running`. `skipped` joins the same path — it means CI decided nothing should run, the same absence of verification that `dispatch_pipeline` already treats as green when there is no pipeline at all, so an MR with no CI shipping instantly while an MR whose CI skipped itself waits forever was an inconsistency, not a policy. The new `fetch_pipeline_jobs` returns **`nil`**, not `[]`, when GitLab is unreachable: `[]` reads as green on this path, so a swallowed API error would be enough to ship an unverified ticket. **`canceled` is deliberately unchanged** and keeps the documented "No blocked state" behaviour: an interrupted run has no verdict to read (its blocking jobs are `canceled`, not `failed`, so the same rule would deliver a ticket whose tests were killed mid-flight), and unlike `manual` the wait usually resolves on its own because a new pipeline supersedes it and `head_pipeline` re-points — the residual unbounded tail belongs to the generic time bound (Autodev #53), not to a second status-specific clock. No activity-log line was added: `handle_green`'s `:pipeline_green` already records the delivery, and a line emitted before it would sit on the wrong side of the Claude-quota gate, appending to the GitLab note on every poll and heading for the 1M-character cap during an outage — so the diagnostic (`Pipeline manual for MR !… : N blocking job(s), none failed → treating as green`) goes to the technical log, and the ticket reads "Pipeline vert" for a pipeline GitLab paints orange. ## [1.0.0-alpha.41] - 2026-07-07

### Fixed

- **Re-implementing an existing branch no longer dies at `git push` with `! [rejected] (stale info)` (task #33).** Surfaced while relaunching the task #32 tickets in prod: once a recette-KO reentry routes to a full re-implementation, `IssueProcessor` reuses the existing branch, rebases it on the (meanwhile-advanced) target (`rebase_branch_on_target`), then pushes — and `RepoOperations#push_with_lease_fallback` failed on the `--force-with-lease` retry. Root cause (reproduced deterministically, git 2.50.1 = prod): the **bare** `git push --force-with-lease` implies `--force-if-includes` since git 2.30, which requires the remote-tracking tip to be integrated into the pushed history; the rebase rewrites history so the previously-delivered remote commit is no longer an ancestor, and the check rejects the push as `stale info`. It bit specifically because the `clone_depth: 1` clone is `--single-branch`, so `refs/remotes/origin/<branch>` exists only via autodev's one-off fetch (a full clone tracks the branch and passes). The force retry now uses an **explicit-value lease** `--force-with-lease=<branch>:<sha>`, where `<sha>` is the fetched `refs/remotes/origin/<branch>` (`RepoOperations#remote_lease`): it keeps the anti-clobber guarantee (still refused if the remote moved past `<sha>` since our fetch) but does not trigger `--force-if-includes`, so a deliberate post-rebase overwrite of our own prior delivery goes through. Falls back to the bare lease when there is no remote-tracking ref (brand-new branch — no force needed anyway). This also covers `MrFixer`'s rebase-then-push path. New `test/repo_operations_force_push_test.rb` reproduces the rebased-branch push (asserts it succeeds) and asserts the lease still refuses a push when the remote genuinely moved since the fetch. Follow-up still open on #33: the error path leaves `next_retry_at` NULL, so a push that ultimately errors is not auto-retried (same orphan pattern as #26).

### Fixed

- Dashboard "Activité de la semaine" sparkline silently showed all-zero bars in production despite thousands of daily activity events. Root cause: `activity_events.created_at` (and `issues.created_at`) are TEXT columns inherited from the pre-rails Sequel schema — the Rails migration's `create_table … if_not_exists: true` is a no-op on the existing prod tables, so the column type stayed TEXT. Because neither model declared `attribute :created_at, :datetime`, ActiveRecord treated `created_at` as a `:string` and serialized the timestamp via `Time#to_s`, storing `"2026-06-11 11:13:03 UTC"` — with a literal ` UTC` suffix. SQLite's `date()` returns NULL on that format, so `weekly_activity_counts`' `GROUP BY date(created_at)` collapsed every recent row under a NULL bucket and the per-day lookup `rows["2026-06-17"]` always missed → `[0,0,0,0,0,0,0]`. (Pre-rails Sequel-written rows were stored without the suffix, so the chart degraded only as AR-written rows accumulated.) Three-part fix: (1) `ActivityEvent` and `Issue` now declare `attribute :created_at, :datetime` so AR emits the suffix-free `'YYYY-MM-DD HH:MM:SS'` format `date()` understands — `Issue` already did this for its other timestamp columns but omitted `created_at` (a latent identical bug on the next AR-written issue). ### Fixed

- Dashboard freezing on repeated F5 / multiple open tabs, requiring a server restart. Root cause: each open browser tab parked one Puma thread on `Queue#pop(timeout: HEARTBEAT_INTERVAL)` in `StreamController#show`; `Queue#pop` does not observe TCP-level disconnects, so a tab that went away stayed parked until the next heartbeat tick caused a `write` to raise `ClientDisconnected`. With the previous 15-second interval and Puma's 10-thread pool, a few quick refreshes saturated the pool and froze every Rails request. Two mitigations: (1) a new `pagehide` listener in `Layout::APP_JS` calls `window.__autodevSSE.close()` so the browser sends a FIN immediately on F5 / tab close / cross-document navigation, releasing the server thread on the very next write instead of waiting for a tick; (2) `HEARTBEAT_INTERVAL` lowered from 15 → 5 seconds as the safety net for silent client deaths (browser killed, network drop, machine sleep). The architectural fix — moving to ActionCable + Solid Cable, which would hijack the socket out of Puma's thread pool entirely — is deferred to the AutoSpec implementation; rationale and decision criteria captured in `docs/autospec.md` §L.
- `Web.config` (which holds `~/.autodev/config.yml`) reverted to `nil` after any code reload in development, because the loader fired in an `after_initialize` block that only runs once at boot, whereas `Web` lives in `app/services/web.rb` and is wiped by Zeitwerk's reloader along with its `@config` instance variable. Any post-reload request that read through `Web.config` then crashed — visibly during the OAuth callback, where `Autodev::GitlabMembershipSync.for_user!` raised `ConfigError (Missing GitLab API token)` despite `~/.autodev/config.yml` carrying a valid `gitlab_token`. Switched the loader to `Rails.application.config.to_prepare`, which still fires once at boot in production but re-runs after every reload in development. Updated the related comment in `config/initializers/devise.rb` so it doesn't point at the old `after_initialize` site.
- `/assets/css/*.css` 404'd in development with a bare `Content-Type: text/plain\nNot found` body — page chrome rendered unstyled and every page was effectively unusable from a fresh `bin/rails server`. Two compounding root causes: (1) `propshaft/railtie` auto-inserts `Propshaft::Server` into the middleware stack whenever `config.public_file_server.enabled` is true (Rails 8 default in development; unset in production where `RAILS_SERVE_STATIC_FILES` gates it); (2) `Propshaft::Server#call` requires a matching digest in the URL — `Asset#fresh?(nil)` returns false, so stable, hand-written URLs like `/assets/css/tokens.css` from our Phlex layout 404 without falling through to the router, regardless of whether the file exists on the load_path. Mission Control's `stylesheet_link_tag`-generated URLs (e.g. `/assets/mission_control/jobs/application-<sha>.css`) DID include a digest, so they hit a different failure mode (no matching Rails route once Propshaft was sidestepped). Fix: drop `Propshaft::Server` from the middleware stack (`config.middleware.delete Propshaft::Server` in `config/application.rb`) and consolidate every `/assets/*` URL onto the rewritten `AssetsController#show` catch-all that does the load_path lookup itself — digest-aware for MCJ's helpers, digest-tolerant for our hand-written URLs. Propshaft's railtie is still loaded (MCJ needs `config.assets.paths`); only the middleware is gone. Production was always on this code path (no static-files flag set) so this restores dev/prod symmetry.

### Fixed

- Dashboard homepage froze the browser after a few normal tab opens or reloads in production (`v1.0.0-alpha.3`). Root cause was a thread-pool deadlock between three layers:
  1. `app/components/web/views/layout.rb` opens `new EventSource('/stream')` on every `turbo:load`, so every page under the layout (including `/`) holds an open SSE connection.
  2. `StreamController#show` (`app/controllers/stream_controller.rb`) parks a Puma thread on `queue.pop` — Ruby's `Queue#pop` is blocking and does not observe the underlying socket. When the client closes the tab or reloads, the thread stays parked until an event arrives (then `response.stream.write` raises and the thread is released). With autodev's recurring poll at 5 min and quiet periods on the EventBus, that's essentially never.
  3. `config/puma.rb`'s `threads 3, 3` capped Puma at 3 threads. Three tabs / reloads / Chrome prefetches in a row → 3/3 threads wedged → every subsequent HTTP request, including `GET /`, queues in Puma's accept queue indefinitely. The browser spins on the URL.
  Fix lives in two files: `StreamController#pump_events!` now calls `queue.pop(timeout: HEARTBEAT_INTERVAL)` (15 s) and writes a `: ping\n\n` SSE comment on every tick — if the client has gone away, `response.stream.write` immediately raises `IOError` / `ClientDisconnected`, the existing `rescue` block unsubscribes the queue, and the thread is released. `config/puma.rb` bumps `RAILS_MAX_THREADS` default from 3 to 10 so a momentary burst of tabs no longer saturates the pool while the heartbeat reclaims dead connections. `config/database.yml`'s `primary` pool also goes from 2 to 10 to match — the pool=2 comment had inherited a constraint from Sequel's `max_connections: 1` contract, but Sequel was removed at `v1.0.0-alpha.1` so the constraint is dead; SQLite still serializes writers at the file level via WAL + `busy_timeout=30000ms`, the AR pool just governs how many connection objects this Puma process holds. The companion `navigator.webdriver` guard in `layout.rb` (below) only paper-over the symptom for browser automation; the thread-pool fix is what restores manual usage.
- `app/components/web/views/layout.rb` opened a `new EventSource('/stream')` on every `turbo:load`, including under browser automation. `/stream` is served by `StreamController#show` via `ActionController::Live` and is intentionally never-ending — the response stays open for the lifetime of the tab and counts as a permanently in-flight request. Any HTTP caller that waits on `networkidle` (Chrome DevTools MCP's `navigate_page`, Puppeteer / Playwright with default `waitUntil: 'networkidle0'`, Lighthouse, …) hangs on every URL under the layout until its own timeout fires — surfaced during the v1.0.0-alpha.3 post-deploy non-regression sweep where `/`, `/issues`, `/issues/:id`, `/errors`, `/projects`, `/list/:status` all timed out under Chrome MCP despite returning healthy responses to plain `curl`. Fix: bail out of the SSE setup when `navigator.webdriver` is truthy. `navigator.webdriver` is set to `true` by every WebDriver / CDP automation channel (Chrome with `--remote-debugging-port` + an attached debugger, Puppeteer headless, Playwright, Selenium), so the live-update channel only goes silent under automation — the dashboard remains fully usable, just without push updates; reloads continue to fetch fresh data. Manual usage is unaffected.
- `config/initializers/session_store.rb` only required `action_dispatch/session/active_record_store` (the Rack middleware), not `active_record/session_store` (the AR-side gem entry that wires `ActionDispatch::Session::ActiveRecordStore.session_class = ActiveRecord::SessionStore::Session`). That left `session_class` nil. Anonymous reads (the existing dashboard) never tripped it because they don't write to session; any controller that DOES write — `protect_from_forgery` on a non-GET, Devise sign-in, Mission Control's controllers — crashed with `NoMethodError: undefined method 'new' for nil` inside `get_session_model`. The latent bug shipped with v1.0.0-alpha.1 (Devise was wired but no controller exercised session writes); MCJ surfaced it on the first `GET /admin/jobs`. Added the missing `require 'active_record/session_store'`.

### Fixed

- `config/recurring.yml` used `"every <N> seconds"` for the `AutodevPollJob` schedule, which Fugit happens to parse as `Fugit::Cron` for small values (≤ a few seconds) but maps to `EtOrbi::EoTime` for anything from 60s upward. Solid Queue's `SolidQueue::RecurringTask#ensure_schedule_supported` validates `parsed_schedule.instance_of?(Fugit::Cron)` and rejects everything else with `"is not a supported recurring schedule"`. Fix: emit a real cron expression instead. `schedule: "*/<%= [ENV.fetch('AUTODEV_POLL_INTERVAL', '300').to_i / 60, 1].max %> * * * *"` rounds the legacy seconds value up to the nearest minute and emits `*/N * * * *` — Fugit always parses that as `Fugit::Cron` and Solid Queue accepts it. Supported range without further editing: 60s to 3540s (1..59 minutes). Beyond that, hand-edit the schedule with hour-level cron syntax. The default 300s = 5 minutes = `*/5 * * * *` keeps the legacy cadence. Local smoke test (with `AUTODEV_POLL_INTERVAL=2`) accidentally hit Fugit's small-seconds-as-cron heuristic and missed this in alpha.1 — caught only on a prod-default-config deploy.

## [0.15.1] - 2026-06-02

### Fixed

- `RateLimitDetector::PATTERN` did not match claude-code's `"You've hit your session limit"` variant — only `"your limit"`, `"rate limit"`, and `"usage limit"` were caught. When the API returned the session-limit phrasing, `RateLimitDetector.check!` silently returned, danger-claude exited non-zero, and the caller raised `ImplementationError` instead of `RateLimitError` — bypassing the rate-limit pause logic in `IssueProcessor::ErrorHandler`, `MrFixer::ErrorHandler`, and `PipelineMonitor::FailureHandler`. Observed in production on Powerpanne issues #15643 / #15737 / #15855 / #15125 / #16044 (2026-06-02): all marked `error` with `"session limit · resets HH:MMam (UTC)"` in stdout when they should have paused and retried. Pattern is now `/you've hit your (?:session |usage )?limit|rate limit|usage limit/i` and covers all three claude phrasings. While auditing, also fixed `RESET_PATTERN` to accept hour-minute formats — the original `(\d{1,2})(am|pm)` regex silently dropped `:30` in `"resets 11:30am (UTC)"`, setting the pause window to the wrong wall-clock time (always on the hour). Now matches both `"6pm"` and `"11:30am"` with minutes parsed and passed to the pause schedule. Six tests in `test/rate_limit_detector_test.rb` cover all three limit phrasings, an unrelated-failure negative case, and both reset-time formats.

- `RepoRebaser#resolve_conflicts_then_continue` did not catch exceptions from `danger_claude_prompt`. When danger-claude itself failed during conflict resolution (rate limit, session limit, or any other non-zero exit), the raise propagated up uncaught, leaving the work tree in a half-rebased state and crashing whatever pipeline was calling the rebase (PipelineFixer, MrFixer, or IssueProcessor). Observed on Powerpanne issue #15643 (2026-06-02) with v0.15.0: pipeline fix attempted, rebase produced a conflict, claude was invoked to resolve, claude hit a session limit, `ImplementationError` propagated through the full call stack (the exact stack frame `repo_rebaser.rb:55 → repo_rebaser.rb:27 → pipeline_monitor/failure_handler.rb:98` confirmed the path). Now wrapped: `RateLimitError` propagates after `git rebase --abort` (the worker still pauses, but the tree is clean for resume); any other exception is logged, the rebase is aborted, and the helper returns `:failed` — the caller falls back to running on the unmodified branch instead of crashing. Two regression tests in `test/repo_rebaser_test.rb` cover the `ImplementationError → :failed + abort` and `RateLimitError → reraise + abort` paths, both verifying via `.git/rebase-{apply,merge}` that the rebase is no longer in progress after the helper returns.

## [0.15.0] - 2026-06-02

### Added

- Auto-rebase the autodev branch onto its target before every write action. Without this, danger-claude operates against a stale tree: when `target_branch` moves forward between Autodev's first push and a later iteration (reentry, MR-fix round, pipeline-fix round), the implementation/fix runs on the old base, MrFixer wrestles with thread positions on lines that have shifted, PipelineFixer sees test failures that wouldn't exist on a rebased branch, and the MR may pile up conflicts before merge. New `RepoRebaser` mixin (included via `DangerClaudeRunner` so all three classes inherit it) exposes `rebase_branch_on_target` — fetches the target with an explicit refspec (so `refs/remotes/origin/<target>` actually exists; `git fetch origin <branch>` alone only writes `FETCH_HEAD` on single-branch clones), skips the rebase if `git log HEAD..origin/<target>` is empty, tries a clean `git rebase`, and on conflict invokes danger-claude with a focused prompt to resolve files (claude stages, the helper runs `git rebase --continue` with `GIT_EDITOR=true` to auto-accept the original commit message). If claude can't resolve, the helper `git rebase --abort`s and returns `:failed` — the branch is left in its pre-rebase state so the downstream action runs on stale-but-clean ground instead of being blocked. Shallow-aware: probes `git rev-parse --is-shallow-repository` and uses `--deepen=500` on shallow clones (500 commits is roughly several weeks of staging activity for Powerpanne, the largest tracked repo), normal fetch on full clones. Three call sites: `IssueProcessor::GitOperations#resolve_branch` (when reusing an existing autodev branch), `MrFixer::FixCycle#run_fix_cycle`, and `PipelineMonitor::FailureHandler#prepare_work_dir`. Five tests in `test/repo_rebaser_test.rb` exercise the helper against a real on-disk bare repo with diverging branches: no-op when target hasn't moved, clean rebase when target advanced without conflict, conflict resolved by claude → rebased and pushed, conflict left untouched by claude → abort + `:failed`, and verifies the abort path actually rewinds HEAD to its pre-rebase SHA.

- `DiscussionSnapshot` instrumentation module that captures a ground-truth snapshot of every MR discussion at three critical moments: `:post_mr_review` (right after mr-review returns successfully), `:pre_fix_dispatch` (in `PipelineMonitor#green_post_review`, just before the AASM routes to `done` vs `fixing_discussions`), and `:pre_mr_fix` (in `MrFixer#process_discussions`). Motivated by Powerpanne issue #11859 (2026-05-28): `green_post_review` saw `count: 0` and transitioned to `done` immediately after the only successful mr-review run of the day, yet 12 unresolved threads were visible on the MR when the user looked. Without per-discussion state captured at both sides of the suspected race (mr-review draft note publication vs autodev's next fetch), the root cause cannot be pinned. Each snapshot records, per discussion: short id, author username, first-note created_at, total/resolvable/resolved note counts, an `unresolved` boolean computed identically to `fetch_unresolved_discussions`'s filter, and a position string (`path:line`, or `path:outdated` when `new_line` is null, or `general` for non-diff comments). Snapshots are logged at DEBUG and persisted as `activity_events` rows with `kind='discussions_snapshot'` so they can be queried via SQL on the prod DB. The module is intentionally defensive — API errors, missing methods, persistence failures are all swallowed — so the instrumentation can never break the workflow it's instrumenting. Web UI displays snapshots in the activity timeline as raw JSON (via `format_event`'s default branch), no template change required. Six tests in `test/discussion_snapshot_test.rb` cover payload shape, position-string variants (general/diff-line/outdated), persistence, and graceful degradation on API failure.

### Fixed

- mr-review failures used to silently loop forever. `Reviewer#launch_review` incremented `review_count` only on success (line 15 of `pipeline_monitor/reviewer.rb`) but fired `issue.review_done!` unconditionally (line 16), so a failing mr-review run sent the issue back to `checking_pipeline` with `review_count` still at 0; the next poll cycle re-entered `green_first_review` and tried mr-review again. With nothing to bound the failure side, a persistently broken mr-review (token expired, binary crash, transient GitLab errors) ran indefinitely. Observed on Powerpanne issue #11859 (2026-05-28): 37 `checking_pipeline → reviewing` transitions in ~100 minutes before a single 15-min run finally succeeded. Now: a new `review_failure_count` column tracks consecutive failures; on success the counter resets, on failure it increments. At `REVIEW_FAILURE_THRESHOLD = 5` consecutive failures, a new AASM event `review_giveup!` fires (`reviewing → done`) with a localized alert (`review_failures_exhausted` notification + `:review_failures_exhausted` activity log) and the issue is reassigned to the author — same UX contract as `max_review_rounds_reached`. The counter is reset in `PollRouter::ResumeHandler` on both reentry paths so a re-engaged ticket starts with a clean slate. Tests: `test/pipeline_monitor_review_failure_test.rb` covers all five behavioural assertions (counter increments, sub-threshold returns to `checking_pipeline`, threshold transitions to `done`, success resets counter, success increments `review_count`); `test_review_giveup_from_reviewing_goes_to_done` in `database_advanced_test.rb` covers the new AASM event.

- Reentry from `done` (user re-adds a `labels_todo` label on a finished issue) always routed back to `pending` and triggered a full re-implementation cycle, even when the existing MR was still open with unresolved review threads. Observed in production on Powerpanne issue #11859 (2026-05-28, MR !10681): the user re-added the `To do` label expecting Autodev to address the 12 outstanding bot/reviewer threads; instead `PollRouter::ResumeHandler#handle_reenter` fired `reenter!` → `pending` → clone → checking_spec → implementing → MR update, and MrFixer never ran (`fix_round` stayed at 0). The reset of `review_count: 0` also forced the pipeline-green path through `green_first_review` (mr-review) instead of `green_post_review` (which is what routes to `fixing_discussions`). `PollRouter::ResumeHandler` now inspects the MR state on reentry: if `mr_iid` is set and the MR is `opened`, fire a new AASM event `reenter_to_check_pipeline` (`done → checking_pipeline`), pin `review_count: 1`, and apply `label_doing` immediately. The next `poll_pipelines` tick in the same cycle picks up the issue and `green_post_review` either dispatches to `fixing_discussions` (unresolved threads exist) or transitions cleanly to `done` (everything already addressed). The original re-implementation path is preserved as the fallback when no MR exists or the MR is closed/merged — that's still the right behavior when the spec changed or the previous work was discarded. `review_count` is pinned to `1` (not preserved) on purpose: preserving a value `>= MAX_REVIEW_ROUNDS` would short-circuit straight back to `done` via the `max_review_rounds_reached?` guard. Tests: new `test/poll_router_reenter_test.rb` covers the three branches (MR open → checking_pipeline, MR closed → pending, no MR → pending), plus a regression on the review_count pin; `test_reenter_to_check_pipeline_from_done` in `database_advanced_test.rb` covers the new AASM event in isolation.

### Fixed

Observed in production: GitLab returning `400 Bad request - Note is too long (maximum is 1000000 characters)` on every poll for notes 821372 and 820384 (Powerpanne issues #15676 and #15839). Root cause: per the "no blocked state" design, an issue with an infra-side pipeline failure stays in `checking_pipeline` indefinitely until manual intervention. On each poll cycle, `PipelineMonitor::FailureHandler#triage_and_fix` emitted two activity-log entries (`pipeline_red` + `pipeline_infra`) that appended unconditionally — at the default `poll_interval: 300`, this added ~576 lines/day (~40 KB/day) and crossed GitLab's 1M-char cap after ~25 days. Once the note crossed the cap, every subsequent `edit_issue_note` returned 400 and the rescue swallowed it, so autodev kept logging the same failure on every tick. Two complementary fixes:
  - **Source-side dedup**: `pipeline_red`, `pipeline_infra`, and `pipeline_evaluating` now pass a `replace_pattern` to `log_activity` so each new emission replaces the previous one in place instead of appending. `ActivityLogger.replace_or_append` also now uses `rindex` to find a match anywhere in the body, not only on the last line — without that, three different recurring events interleaved on the same poll cycle would each break the next one's dedup because the "last line" is whatever the previous event in the same cycle just appended (the existing `pipeline_checking` dedup was already affected by this in the failing-pipeline path).
  - **Sink-side size guard**: `ActivityLogger.upsert` now checks `body.length > MAX_NOTE_BYTES` (900_000, conservative under GitLab's 1M cap) and truncates if needed. Strategy: keep the 2-line header, inject a localised marker (`activity_truncation_marker`, FR/EN), then keep the most recent tail lines that fit under the budget — older entries fall off. Idempotent: the marker is recognised and skipped on subsequent truncations so it doesn't stack. This also auto-repairs the existing oversized notes on the next emission: GET returns the >1M body, the guard truncates it, and the PUT succeeds.

  Three regression tests in `test/activity_logger_overflow_test.rb` cover both layers and the FR/EN marker selection. Verified the rindex regression specifically by temporarily reverting to the `lines.last` semantics — the corresponding test failed immediately with "replaces match not at tail".

## [0.11.6] - 2026-04-20

### Fixed

- Follow-up on the v0.11.5 single-connection switch: workers were hitting `Sequel::PoolTimeout: timeout: 5.0` because Sequel's default pool timeout is 5s. With `max_connections: 1`, any caller mid-iteration on a dataset holds the connection through the entire loop (SQLite keeps the cursor open across `.each`), and if the loop body does slow external I/O — as `poll_unassignment` and `poll_done_unassigned` do, with GitLab API calls per issue — workers waiting for the connection blow through 5s.
  - Raised `pool_timeout` to 60s for SQLite.
  - Materialized the two `poll_unassignment`/`poll_done_unassigned` iterations with `.all.each` so the DB connection is released before GitLab calls run. Applied the same shape defensively to `poll_pipelines` / `poll_discussions` for consistency, though their loop bodies only enqueue (fast).
- Startup log now includes `pool_timeout` alongside `journal_mode`/`busy_timeout`/`max_connections` so the effective pool config is visible without re-instrumenting.

## [0.11.5] - 2026-04-20

### Fixed

- SQLite `database is locked` errors are finally gone. The v0.11.2–v0.11.4 attempts relied on Sequel's `after_connect` hook to apply per-connection PRAGMAs/busy_handler to every pooled connection; in practice the hook did not fire in our setup (confirmed in logs: `busy_timeout=0ms` at startup, no `[DB-LOCK]` dumps under contention), which is why increasing timeouts and adding defensive handlers changed nothing. Switched to `max_connections: 1` so Sequel's `ThreadedConnectionPool` serializes all DB access through a Ruby mutex. For SQLite this is strictly better: writes are already serialized at the file level, so multiple pool connections only add contention (and trigger `BusyException` when writers collide). `journal_mode=WAL` and `busy_timeout=30000` are now applied directly to the single connection via `@db.run`. Startup logs the effective values so they're visible without re-instrumenting.
- Dropped the unused `after_connect`, `busy_handler`, and thread-backtrace dump code added in v0.11.3–v0.11.4 — the root-cause fix makes them moot.

## [0.11.4] - 2026-04-20

### Added

- SQLite `busy_handler` now dumps all thread backtraces to stderr after 20 retries on the same contention episode (prefixed `[DB-LOCK]`). Since the handler runs in the thread that is waiting for the lock, the dump captures what every other thread is doing at the exact moment of contention — making it possible to identify which operation is holding the write lock. Diagnostic only; does not change the retry policy.
